# 01. 大模型与机器学习最小基础

## 1. 为什么应用开发者也要懂一点机器学习

做大模型应用，不一定要会训练模型，但需要理解模型为什么这样工作。否则你会在调试时遇到很多看起来“玄学”的问题：

- 为什么同一个问题两次回答不一样？
- 为什么明明给了资料，模型还是答错？
- 为什么上下文太长以后效果变差？
- 为什么 RAG 检索出来的内容对，但最终答案还是不稳定？
- 为什么微调不是所有问题的答案？

这些问题不需要你掌握完整机器学习理论，但需要知道大模型的基本工作方式。

本章会按下面这条知识线展开：

```text
机器学习、深度学习、大模型的关系
  -> 训练、推理、微调、量化、蒸馏
  -> Token、词表、上下文窗口
  -> Transformer、Attention
  -> 幻觉、随机性、推理参数
```

先把这些概念放在一张地图里，后面学习 API、Prompt、RAG、Agent 时才不会只是在记名词。

## 2. 机器学习、深度学习、大模型的关系

可以用三层关系理解：

```text
人工智能 AI
  -> 机器学习 Machine Learning
      -> 深度学习 Deep Learning
          -> 大语言模型 Large Language Model
```

机器学习的核心是让程序从数据中学习规律，而不是只靠人工写规则。

深度学习是机器学习中的一类方法，通常使用多层神经网络处理复杂数据，比如文本、图片、语音。

大语言模型是深度学习在自然语言方向上的重要成果。它通过大量文本训练，学会根据上下文预测、生成和改写文本。

这里有一个很重要的直觉：

```text
传统规则程序：人写规则 -> 程序按规则执行
机器学习模型：数据里有规律 -> 模型学出规律 -> 根据新输入做预测
大语言模型：大量文本里有语言和知识模式 -> 模型学出生成下一个 Token 的能力
```

所以大模型不是把所有知识逐条存进一个“答案表”。它更像一个从海量文本里学到语言模式、概念关系和表达习惯的生成器。它能把很多信息组合起来回答问题，但它不会像数据库那样天然保证事实精确。

这也是为什么应用开发者需要关心“边界”：

- 问通用解释、代码思路、文本改写，大模型通常很有用。
- 问实时库存、用户余额、最新订单，应该查数据库或业务接口。
- 问企业内部文档，应该通过 RAG 提供资料。
- 问高风险决策，应该让程序校验或让人确认。

## 3. 训练、推理、微调、量化、蒸馏

训练和推理是两个阶段。

训练是模型学习能力的过程。它需要大量数据、GPU 算力和训练框架。普通应用开发者通常不会从零训练大模型。

推理是使用模型的过程。你调用 API，传入问题、上下文、工具定义，模型返回结果。大多数大模型应用开发都发生在推理阶段。

```text
训练：数据 -> 模型学习 -> 得到模型参数
推理：用户输入 -> 模型计算 -> 生成回答
```

可以把训练理解成“培养一个人的长期能力”，把推理理解成“让这个人现场完成一次任务”。

训练阶段会决定模型的大能力边界：会不会写代码、会不会理解中文、会不会看图、会不会遵循指令。推理阶段决定这一次任务做得好不好：你给了什么背景、问题是否清楚、输出格式是否明确、是否允许调用工具。

现实里的大模型训练通常还会分成几层：

- 预训练：从大量文本中学习语言规律和通用知识。
- 指令微调：学习按照人类指令完成任务。
- 对齐和偏好优化：让回答更安全、更符合人类偏好。
- 领域微调：让模型更适应某类固定任务或表达风格。

### 训练

训练是在改变模型参数。可以把模型参数理解成模型内部大量“权重数字”，这些数字共同决定模型看到输入后会怎么计算、怎么生成。

预训练通常规模最大，目标是让模型从海量文本、代码、图片或语音中学习通用规律。它决定模型的基础能力，比如语言理解、常识、代码模式和多语言表达。

应用开发者通常不做预训练，因为成本很高，而且需要数据治理、训练框架、GPU 集群和模型评估体系。

### 推理

推理是不改变模型参数，只使用模型完成一次任务。

你调用模型 API 时，传入的 Prompt、历史消息、RAG 资料、工具定义、推理参数，都属于这一次推理的输入。模型会基于这些输入生成输出，但模型本身不会因为这次请求永久学会新知识。

所以“我刚才告诉过模型，为什么它下次不记得？”这个问题的答案通常是：应用没有把这段信息保存下来并重新放回上下文。

### 微调

微调是在已有模型基础上继续训练，让模型更适应某类任务、语气、格式或领域表达。

它适合解决这类问题：

- 固定任务模式：例如总是按某种格式做客服质检。
- 固定表达风格：例如回答更像公司内部客服话术。
- 固定领域样本：例如大量相似合同条款分类。

它不适合解决这类问题：

- 实时业务数据，比如库存、订单、用户状态。
- 高频变化知识，比如每天更新的项目文档。
- 权限控制，比如谁能查看什么数据。

这些更适合数据库、工具调用或 RAG。

### 量化

量化是把模型里的数字用更低精度表示，从而降低显存、内存和推理成本。

可以粗略理解为：原来模型参数用很精细的小数保存，现在用更粗的数字保存。这样模型更小、跑得更快、部署门槛更低，但能力可能有损失。

例如端侧或本地部署时，经常会看到 8-bit、4-bit 这类说法。数字越低，通常越省资源，但输出质量、稳定性或长文本能力可能下降。

量化不改变模型“学过什么”的本质，它主要改变模型运行时的资源占用和精度表现。

### 蒸馏

蒸馏是用一个更强的大模型去训练或指导一个更小的模型，让小模型学习大模型的输出方式。

可以把它理解成“老师模型带学生模型”。老师模型能力强但成本高，学生模型能力弱一些但更便宜、更快、更容易部署。

蒸馏常见目标：

- 降低推理成本。
- 提高响应速度。
- 让小模型适配某个固定任务。
- 让端侧或私有化部署更现实。

蒸馏不是简单复制大模型。小模型容量有限，不可能完整继承老师模型的全部能力，所以通常适合边界清楚、任务固定的场景。

把这几个概念放在一起看：

| 概念 | 是否改变模型参数 | 主要目的 | 应用开发者常见关系 |
| --- | --- | --- | --- |
| 训练 | 是 | 从数据中学习能力 | 通常不从零做 |
| 推理 | 否 | 使用模型完成任务 | 每天调用 API 做的事 |
| 微调 | 是 | 适配任务、风格、领域 | 少数稳定场景才需要 |
| 量化 | 通常不重新学习能力 | 降低资源和成本 | 本地/端侧部署常见 |
| 蒸馏 | 是，训练小模型 | 用小模型模仿大模型 | 固定任务降本常见 |

对应用开发者来说，最关键的是不要把“模型能力不足”和“这次输入没组织好”混在一起。很多时候，换模型不是第一步，先把上下文、Prompt、工具和输出校验做好，收益更直接。

对应用开发者来说，重点是推理阶段的工程能力：

- 如何组织输入
- 如何控制输出格式
- 如何接入业务数据
- 如何调用工具
- 如何评估结果质量
- 如何控制成本和延迟

一个简单判断：

```text
如果问题是“模型不会这种能力”，可能需要换模型或微调。
如果问题是“模型这次没拿到足够信息”，优先改上下文、RAG 或工具调用。
如果问题是“模型输出不稳定”，优先改 Prompt、结构化输出和评估集。
```

## 4. Token、词表与 tokenizer

大模型不是直接按“字”或“词”理解文本，而是会先把文本切成 Token。

Token 可以粗略理解为模型处理文本的最小片段。英文里一个单词可能是一个或多个 Token，中文里一个字、一个词、一个符号也可能被切成不同 Token。

更准确一点说，模型看到的不是原始文字，而是一串 Token ID。文本会先经过 tokenizer，被切成模型词表里的片段，再转换成数字。

词表就是模型认识的 Token 清单。每个 Token 会对应一个数字 ID。

可以用一个简化例子理解：

```text
原始文本：Android 崩溃日志
tokenizer 切分：["Android", " 崩", "溃", "日志"]
词表映射：[5021, 38120, 7742, 19087]
模型真正看到的是：5021 38120 7742 19087
```

不同模型的词表不一样，同一句话在不同模型里可能被切成不同 Token。中文、英文、代码、空格、标点、换行都可能影响切分结果。

例如下面这几类内容都会消耗 Token：

- 用户的问题
- 系统提示词
- 历史对话
- RAG 检索出来的资料
- 工具调用参数和返回结果
- 模型最终输出

不同模型的 tokenizer 不一样，所以不要死记“一个中文等于几个 Token”。工程上更稳妥的做法是：用当前模型提供的计数工具或 SDK 估算，而不是凭感觉估。

你需要关心 Token，是因为它影响三个重要问题：

1. 上下文长度：一次请求最多能放多少内容。
2. 成本：很多模型按输入和输出 Token 计费。
3. 速度：Token 越多，请求通常越慢。

在工程上，不要把整个项目、整本文档、所有日志都直接塞给模型。应该先筛选、压缩、检索，再把最相关的内容放进上下文。

边界也要记住：Token 只是切分单位，不等于“理解单位”。模型真正理解内容，还要经过后面的向量表示、注意力计算和层层变换。你可以把 Token 看成“进入模型前的原材料切片”。

## 5. 上下文窗口：一次请求能看见多少内容

上下文窗口是模型一次请求能看到的最大内容范围。

比如你把用户问题、系统提示词、历史消息、知识库片段、工具返回结果都放进请求，这些内容都会占用上下文窗口。

它很像一次会议桌的桌面：桌面越大，能摊开的资料越多，但人真正能抓住重点，还是取决于资料是否相关、是否整理过、重点是否突出。

上下文窗口不是越大越好。窗口越大，通常会带来：

- 成本增加
- 延迟增加
- 无关信息干扰
- 关键内容被稀释

所以大模型应用的关键能力之一，就是控制上下文质量。

上下文窗口还有两个容易误解的地方。

第一，它不是长期记忆。模型在一次请求里只能看到你放进去的内容。所谓“记住用户偏好”，通常是应用把用户画像、历史摘要或数据库记录重新放回上下文，而不是模型自己永久记住了这次对话。

第二，放得进去不代表用得好。长上下文里如果混入大量无关内容，模型可能会忽略关键证据，或者被无关片段带偏。实践中经常需要做：

- 历史对话摘要
- 文档分块
- 检索排序
- 重要证据前置
- 对低相关内容做压缩或丢弃

原理认知上，你要记住一句话：

```text
上下文窗口解决“能不能看见”，不自动解决“能不能抓住重点”。
```

## 6. Embedding 是什么

Embedding 是把文本、图片等内容转换成向量。

向量可以理解为一串数字，用来表示内容的语义特征。两个文本语义越接近，它们的向量距离通常越近。

例如：

```text
"Android 应用崩溃日志怎么分析"
"如何排查 App Crash"
```

这两句话字面不完全一样，但语义接近。Embedding 可以帮助系统找到这种相似关系。

Embedding 是 RAG、知识库问答、语义搜索的基础。

可以把 Embedding 想成“语义坐标”。每段文本被放到一个高维空间里，意思接近的内容位置更近。

普通关键词搜索更像查字面匹配：

```text
查“崩溃” -> 命中包含“崩溃”的文档
```

Embedding 搜索更像查语义相近：

```text
查“App 闪退怎么排查”
  -> 可能命中“Crash 日志分析”
  -> 可能命中“NullPointerException 定位”
  -> 可能命中“启动页异常退出”
```

但 Embedding 也有边界：

- 它擅长找相似内容，不擅长做精确权限判断。
- 它能找到相关段落，但不能保证段落里的事实一定正确。
- 它不替代数据库索引，比如订单号、手机号、ID 查询仍然应该走精确查询。
- 它不理解业务最新状态，除非你的索引及时更新。

所以 RAG 系统里通常会把向量检索和关键词检索、权限过滤、时间过滤、重排序结合起来，而不是只靠一个向量距离。

## 7. Transformer 与 Attention 的直观理解

现代大语言模型大多基于 Transformer 架构。你不需要先掌握数学细节，但要理解它解决了什么问题。

Attention 可以粗略理解为：模型在生成某个词时，会动态判断上下文里哪些内容更重要。

例如用户问：

```text
帮我分析这个 Android 崩溃日志，重点看 NullPointerException。
```

模型生成答案时，会更关注：

- 崩溃堆栈
- 异常类型
- 触发位置
- 相关代码上下文

而不是同一段输入里的无关内容。

这就是 Attention 的直觉：根据当前生成目标，对上下文做动态关注。

Transformer 的一个关键特点是，它能让输入中的不同 Token 彼此“看见”并建立关系。比如一句话里有变量名、异常类型、行号、方法调用，模型会在多层计算中不断组合这些信息。

以代码分析为例：

```text
NullPointerException at LoginActivity.onCreate(LoginActivity.kt:42)
```

模型不会只看 `NullPointerException` 这个词，还会结合：

- 出现在哪个类
- 出现在哪个方法
- 行号指向哪里
- 前后堆栈有什么调用关系
- 用户要求它重点分析什么

这就是为什么大模型能处理比较复杂的文本关系。

不过 Attention 不是魔法。它不能保证模型一定选中正确证据，也不能保证模型理解了真实业务含义。上下文噪声太多、提示词目标不清、证据互相矛盾时，模型仍然可能关注错重点。

再补一个推理直觉：很多文本模型是自回归生成的，也就是一次生成一个 Token，前面生成的内容会影响后面的内容。

```text
已有上下文 + 已生成内容 -> 预测下一个 Token -> 再预测下一个 Token
```

所以开头如果走偏，后面可能会沿着错误方向越写越像真的。这也是结构化输出、分步骤约束和结果校验重要的原因。

## 8. 随机性与推理参数

调用模型时，经常会看到一些参数。先理解这几个就够了。

大模型生成答案时，并不是每一步都只有一个唯一正确的下一个 Token。很多时候，它会在多个可能 Token 之间做选择。

例如用户问：

```text
帮我解释一下 RAG。
```

模型下一步可能生成：

- RAG 是一种...
- RAG 可以理解为...
- RAG 的核心思想是...

这些开头都合理。模型会根据概率分布、上下文和推理参数选择其中一种路径。路径不同，后面的答案也会略有不同。这就是为什么同一个问题多问几次，回答可能不完全一样。

随机性不是坏事。它让模型能做创意、改写、头脑风暴和多方案生成。但在代码、配置、JSON、事实问答里，随机性太高会带来不稳定。

### temperature

控制输出随机性。

- 低 temperature：回答更稳定，适合代码、结构化输出、知识问答。
- 高 temperature：回答更发散，适合创意写作、头脑风暴。

### top_p

控制模型从多大概率范围里选择输出。它也会影响随机性，通常不要和 temperature 同时大幅调整。

### max_tokens

限制模型最多输出多少 Token。它可以控制成本和输出长度，但设置太小会导致回答被截断。

### stop

指定遇到某些内容时停止生成。某些结构化任务里会用到。

这些参数不是“质量开关”。它们更像方向盘和刹车，只能调节生成行为，不能凭空补充知识。

常见建议：

| 场景 | 参数倾向 |
| --- | --- |
| 代码生成、JSON 输出、事实问答 | 较低 temperature |
| 头脑风暴、文案、多方案创意 | 稍高 temperature |
| 输出容易太长 | 限制 max_tokens，并要求先给摘要 |
| 输出必须可解析 | 使用结构化输出能力，必要时加程序校验 |

如果一个问题缺少可靠资料，降低 temperature 只能让模型更稳定地给出一个看似确定的答案，并不等于答案一定正确。

推理参数的边界：

- 它们能影响回答稳定性，但不能补知识。
- 它们能限制输出长度，但不能保证内容完整。
- 它们能让格式更可控，但最好配合结构化输出和程序校验。
- 它们不能替代 RAG、工具调用、权限控制和评估。

所以调参前先判断问题来源：

```text
资料缺失 -> 补上下文、RAG 或工具
格式不稳 -> 改 Prompt、结构化输出、校验
回答发散 -> 降低 temperature 或收紧任务
回答截断 -> 调整 max_tokens 或要求分段输出
事实错误 -> 查检索、来源、工具和评估集
```

## 9. 幻觉：为什么模型会一本正经地答错

幻觉是指模型生成了看起来合理但实际错误的内容。

原因可以这样理解：

大模型本质上是在根据上下文生成最可能的文本，而不是像数据库一样精确查询事实。

它的训练目标让它很擅长“生成连贯文本”。当上下文不足时，它可能会根据常见模式补全缺失信息。这种补全在写作、总结、代码草稿中很有用，但在事实问答里就会变成风险。

常见幻觉来源：

- 用户问题本身信息不足
- Prompt 没有限制回答边界
- 上下文里没有可靠资料
- RAG 检索结果不相关
- 模型被要求回答它不知道的内容
- 输出格式太自由

工程上的缓解方式：

- 给模型提供可靠上下文
- 要求引用来源
- 不知道时允许回答“不确定”
- 对关键字段做程序校验
- 对高风险操作加人工确认
- 用测试集做回归评估

一个实用边界是：

```text
允许模型生成解释、建议、摘要和候选方案。
不要让模型单独决定事实、权限、金额、删除、发送、支付等关键动作。
```

这些关键动作应该由程序、数据库、规则系统或人工确认兜底。大模型可以参与判断，但不应该成为唯一事实来源。

## 10. 微调、RAG、Prompt 的区别

这三个概念很容易混。

Prompt 是在请求时告诉模型当前任务怎么做。

RAG 是在请求前先从知识库检索资料，再把资料交给模型回答。

微调是用训练数据改变模型的行为习惯或领域能力。

它们的区别可以用一句话记：

```text
Prompt 改“这次怎么做”
RAG 改“这次参考什么资料”
微调改“模型长期更像什么样”
工具调用改“模型能操作什么真实系统”
```

简单判断：

| 问题 | 优先方案 |
| --- | --- |
| 输出格式不稳定 | Prompt + 结构化输出 |
| 需要回答企业内部文档 | RAG |
| 需要固定风格或特定任务能力 | 微调 |
| 需要实时业务数据 | 工具调用 |
| 需要执行多步骤任务 | Agent |

举几个更贴近开发的例子：

- 想让模型每次按固定字段输出崩溃分析结果，先做 Prompt 和结构化输出。
- 想让模型回答公司内部 SDK 使用方式，先做 RAG。
- 想让模型读取某个用户的真实订单状态，必须走工具或业务接口。
- 想让模型长期适应某种客服话术，才考虑微调。
- 想让模型自动“查日志 -> 看代码 -> 总结问题 -> 给修复建议”，才进入 Agent 范畴。

微调尤其容易被误用。微调可以改变模型的表达习惯和任务模式，但不适合存放频繁变化的事实。比如把最新产品价格、用户订单、项目文档都拿去微调，通常不是好方案；这些内容更适合数据库、工具调用或 RAG。

## 11. 应用开发者当前需要掌握到什么程度

第一阶段只需要掌握这些判断：

- 大模型不是数据库，不能默认相信它的事实性。
- 上下文质量比上下文数量更重要。
- Prompt 负责指导行为，RAG 负责补充知识，工具调用负责连接业务系统。
- 微调不是第一选择，很多问题先用 Prompt、RAG、工具调用解决。
- Android 端通常不应该直接持有模型 API Key。

## 12. 本章学习检查点

读完本章，可以用下面问题检查自己是不是真的理解了原理直觉：

- 我能不能解释“大模型生成答案”和“数据库查询答案”的区别？
- 我能不能说出训练、推理、微调、量化、蒸馏分别是什么意思？
- 我能不能解释词表、tokenizer、Token ID 之间是什么关系？
- 我能不能解释 Token 为什么会影响成本、速度和上下文长度？
- 我能不能解释上下文窗口为什么不是长期记忆？
- 我能不能说明 Embedding 适合语义相似检索，但不适合精确业务查询？
- 我能不能说出 Attention 帮模型解决了什么问题，以及它解决不了什么？
- 我能不能解释为什么同一个问题多次回答可能不同？
- 我能不能说出 temperature、top_p、max_tokens、stop 分别控制什么？
- 我能不能判断一个问题该用 Prompt、RAG、工具调用还是微调？

如果这些问题答不上来，先不要急着学 Agent。因为 Agent 只是把 Prompt、上下文、工具和多轮推理组合起来，基础不稳时会更难调试。
