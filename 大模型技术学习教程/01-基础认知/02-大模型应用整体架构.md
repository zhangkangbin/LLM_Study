# 02. 大模型应用整体架构

## 1. 大模型应用和普通应用有什么不同

普通应用通常是确定性的。

用户点击按钮，前端调用接口，后端查询数据库，返回固定格式的数据。只要输入一样，输出大概率一样。

大模型应用多了一个不确定的智能层。

```text
普通应用：
用户 -> UI -> 后端接口 -> 数据库 -> 返回结果

大模型应用：
用户 -> UI -> 后端服务 -> 模型 / 工具 / 知识库 -> 生成结果
```

这个智能层带来了新的能力，也带来了新的工程问题：

- 输出可能不稳定
- 响应可能较慢
- 成本按 Token 或调用次数计算
- 需要处理幻觉
- 需要控制工具调用权限
- 需要记录模型调用过程，方便回放和排查

从原理上看，普通应用的核心是“确定性流程”，大模型应用的核心是“概率生成 + 工程约束”。

普通接口更像函数：

```text
同样输入 -> 同样代码路径 -> 同样返回结构
```

大模型调用更像一次带上下文的现场推理：

```text
任务说明 + 用户输入 + 上下文 + 参数 + 模型状态 -> 生成一个高概率答案
```

所以你不能只问“模型会不会回答”，还要问：

- 模型回答时看到了哪些信息？
- 这些信息是否可靠、完整、相关？
- 模型有没有权限调用真实工具？
- 输出能不能被程序校验？
- 错了以后能不能回放现场？

这几个问题决定了大模型应用为什么天然需要架构设计，而不是简单把用户输入转发给模型。

## 2. 一个典型的大模型应用架构

可以先用这个通用结构理解：

```text
客户端
  -> 业务后端
      -> Prompt 组装
      -> 上下文管理
      -> 知识库检索
      -> 工具调用
      -> 模型 API
      -> 结果校验
      -> 日志与评估
```

每一层都有明确职责。

客户端负责交互体验，比如输入、流式展示、语音、图片、文件上传。

业务后端负责安全、权限、上下文、业务数据、模型调用和结果校验。

知识库负责提供企业文档、项目代码、产品说明、FAQ 等外部知识。

工具系统负责调用真实业务能力，比如查订单、查数据库、执行代码扫描、读取日志。

模型负责理解任务、生成答案、规划步骤或决定调用哪个工具。

这套架构的背后，其实是在拆四类问题：

| 问题类型 | 由谁解决 | 原理直觉 |
| --- | --- | --- |
| 模型不知道业务事实 | 知识库 / 工具 | 把外部事实放进上下文或通过接口查询 |
| 模型输出不稳定 | Prompt / 结构化输出 / 校验 | 把生成空间收窄，让程序能检查 |
| 模型可能越权操作 | 后端权限 / 人工确认 | 模型只提出意图，真实动作由系统控制 |
| 效果难以持续优化 | 日志 / Trace / 评估 | 保存输入、检索、工具、输出，才能复盘 |

一个成熟的大模型应用，通常不是“模型越强，代码越少”。恰恰相反，模型越接近真实业务，越需要周围的工程系统把边界、证据、权限和评估补上。

## 3. Android、前端、后端分别做什么

### Android 端

Android 端适合负责：

- 用户输入
- 聊天界面
- 流式文本展示
- 语音输入
- TTS 播放
- 图片、文件选择
- 本地日志收集
- 用户授权与隐私提示

Android 端不适合直接做：

- 保存模型 API Key
- 直接访问企业知识库
- 执行高权限工具调用
- 暴露内部 Prompt
- 保存完整敏感对话记录

推荐结构：

```text
Android App -> 你的业务后端 -> 模型服务
```

背后的原理不是 Android 不能发 HTTP 请求，而是模型调用涉及很多不适合放在端上的控制能力：

- API Key 需要保密。
- Prompt 可能包含业务策略。
- 用户权限需要后端统一判断。
- 模型成本需要集中统计。
- RAG 和工具调用通常依赖内部系统。
- 失败日志和评估数据需要统一回收。

Android 端更适合做“体验层”：让用户输入顺、等待过程清楚、结果展示舒服、失败可重试、敏感权限有提示。

### 后端

后端是大模型应用的核心控制层。

后端适合负责：

- 用户鉴权
- API Key 管理
- Prompt 模板管理
- 会话上下文管理
- RAG 检索
- 工具调用
- 成本统计
- 日志追踪
- 风控和权限控制

后端应该把模型当成一个能力组件，而不是让模型直接接管整个系统。

后端控制层有一个很重要的原则：

```text
模型负责建议，系统负责决定。
```

例如模型可以判断“用户可能想查询订单”，但是否真的查订单、查哪个用户的订单、返回哪些字段，应该由后端根据登录态、权限和业务规则决定。

如果让模型直接拼 SQL、直接操作数据库、直接决定调用高权限接口，短期 Demo 可能很快，长期会很危险。

### 前端

如果是 Web 前端，主要关注：

- Chat UI
- Markdown 渲染
- 代码块展示
- 文件上传
- 流式响应
- 任务状态展示
- 人工确认界面

前端体验会显著影响用户对大模型能力的感知。模型慢一点没关系，但界面必须让用户知道系统正在做什么。

大模型应用里的前端还承担一个特殊职责：把“不确定过程”变成“可理解过程”。

比如用户等待时，界面可以展示：

- 正在理解问题
- 正在检索知识库
- 正在调用工具
- 正在生成答案
- 需要用户确认

这不是装饰，而是降低用户焦虑、避免误操作、提高信任感的产品机制。

## 4. Chat、RAG、Agent、多模态的关系

这几个概念可以按能力增强来理解。

Chat 是最基础的对话能力。用户问，模型答。

RAG 是给模型外挂知识库。模型回答前，系统先检索相关资料。

Agent 是让模型能够规划步骤、调用工具、观察结果，再继续执行。

多模态是让模型处理文本之外的信息，比如图片、音频、视频。

```text
Chat：会对话
RAG：会查资料
Tool Calling：会调用工具
Agent：会多步骤做事
Multimodal：会看图、听音频、处理多种输入
```

它们不是互斥关系。一个完整产品里经常会组合使用。

从原理上可以这样区分：

| 能力 | 解决的问题 | 不能解决的问题 |
| --- | --- | --- |
| Chat | 让模型理解输入并生成回复 | 不保证知道你的私有资料 |
| RAG | 给模型补充外部知识 | 不保证模型一定按资料回答 |
| Tool Calling | 让模型连接真实系统 | 不等于模型可以无权限执行动作 |
| Agent | 让模型多步骤规划和执行 | 不等于任务可以无限自动化 |
| Multimodal | 让模型处理图片、语音等输入 | 不等于所有模态都适合端侧处理 |

可以把它们理解成逐层增强：

```text
Chat 解决表达
RAG 解决知识边界
Tool Calling 解决真实动作和实时数据
Agent 解决多步骤任务组织
Multimodal 解决输入输出形式扩展
```

很多项目一开始不需要 Agent。只要问题是“基于资料回答”，RAG 足够；只要问题是“查一个业务状态”，工具调用足够；只有当任务需要循环规划、观察结果、调整下一步时，才需要 Agent。

例如 Android 崩溃分析助手：

```text
用户上传崩溃日志
  -> RAG 检索项目文档和历史问题
  -> 模型分析堆栈
  -> 工具读取 git diff
  -> 生成结构化 Review
  -> 前端展示风险等级和修改建议
```

这个例子里每一步都对应一个原理问题：

- 上传崩溃日志：给模型任务输入。
- RAG 检索项目文档：补充模型训练时不知道的项目知识。
- 模型分析堆栈：利用语言和代码理解能力做推理。
- 工具读取 git diff：获取实时、精确的代码变化。
- 结构化 Review：把自由文本收敛成可展示、可评估的结果。
- 风险等级展示：让人能快速判断下一步动作。

## 5. 云端模型、本地模型、端云混合

### 云端模型

优点：

- 能力强
- 接入快
- 不需要自己维护 GPU
- 模型更新快

缺点：

- 有网络依赖
- 有调用成本
- 数据需要出端
- 延迟不可完全控制

### 本地模型

优点：

- 数据不出本地
- 可离线
- 可私有化
- 长期成本可控

缺点：

- 部署复杂
- 需要算力
- 模型能力可能弱于顶级云模型
- 运维成本高

### 端云混合

对 Android 产品来说，端云混合经常更现实：

- 简单意图识别可以放本地
- 复杂推理走云端
- 敏感数据尽量本地处理或脱敏后上传
- 语音唤醒在端侧
- ASR、LLM、TTS 根据成本和体验选择端侧或云端

这里的核心不是“云端高级、本地低级”，而是推理位置不同。

云端模型把模型权重和算力放在服务商或自己的服务器上，端侧只负责请求和展示。本地模型把模型权重和推理过程放到本机或设备上。

选择时可以按四个问题判断：

- 数据能不能出端？
- 延迟要求有多高？
- 设备算力够不够？
- 模型能力是否满足任务？

例如“离线语音唤醒”适合端侧，“复杂代码分析”更适合云端或服务器，“敏感文本摘要”可能需要本地模型或私有化部署。

## 6. 大模型应用的核心工程闭环

一个能上线的大模型应用，不只是调通 API。

你需要建立闭环：

```text
需求定义
  -> Prompt / RAG / Tool 设计
  -> 模型调用
  -> 输出校验
  -> 用户反馈
  -> 日志回放
  -> 测试集评估
  -> 持续优化
```

如果没有评估和日志，你会很难回答这些问题：

- 这个 Prompt 改完是变好了还是变差了？
- 哪些问题最容易答错？
- 用户失败最多的场景是什么？
- 是模型问题、检索问题，还是业务上下文问题？
- 成本为什么突然升高？

评估和日志的原理意义是：把一次随机生成变成可比较的工程对象。

你至少应该记录：

- 用户输入
- 系统 Prompt 版本
- 检索到的文档片段
- 工具调用参数和结果
- 模型名称和推理参数
- 最终输出
- 用户反馈或人工标注

这样你才能判断一次改动究竟影响了哪一层。否则 Prompt 改了、检索策略改了、模型换了、数据更新了，最后只能靠感觉判断效果。

## 7. Android 大模型应用的推荐基础架构

一个稳妥的 Android 架构可以这样设计：

```text
Android App
  -> API Gateway
      -> Auth
      -> Conversation Service
      -> Prompt Service
      -> RAG Service
      -> Tool Service
      -> Model Provider
      -> Log / Trace / Eval
```

Android 端只处理用户体验和本地能力。

业务后端控制安全、上下文和模型调用。

模型提供商可以替换，比如云模型、本地模型、OpenAI-compatible 服务。

这样做的好处是：

- API Key 不暴露在 App 中
- Prompt 可以后端动态更新
- 模型可以切换
- 日志可以统一追踪
- 用户权限可以统一控制
- 后续接入 RAG 和 Agent 更自然

## 8. 本章学习检查点

读完本章，可以用下面问题检查自己：

- 我能不能解释为什么大模型应用不是“前端直接调模型 API”？
- 我能不能说清客户端、后端、知识库、工具和模型各自解决什么问题？
- 我能不能判断一个需求是 Chat、RAG、Tool Calling 还是 Agent？
- 我能不能解释为什么模型调用需要日志和 Trace？
- 我能不能说明端侧模型、云端模型、端云混合的取舍？
- 我能不能设计一个最小但安全的 Android 大模型应用链路？

如果这些问题能回答，说明你已经不只是会“调用模型”，而是开始理解大模型应用为什么要这样分层。

## 9. 本章小结

大模型应用的本质不是“App 直接问模型”，而是把模型作为一个智能能力嵌入现有系统。

对你来说，最重要的架构判断是：

```text
Android 负责体验
后端负责控制
知识库负责事实
工具负责动作
模型负责理解与生成
评估负责持续改进
```

下一章会把学习路线和实践方向整理出来，帮助你知道后面每个阶段该怎么学、做什么 Demo。
