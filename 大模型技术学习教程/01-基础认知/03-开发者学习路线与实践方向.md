# 03. 开发者学习路线与实践方向

## 1. 不建议从传统机器学习路线开始

如果你的目标是做大模型应用，不建议一开始按下面路线学习：

```text
高等数学 -> 线性代数 -> 概率论 -> 传统机器学习算法 -> 深度学习框架 -> 从零训练模型
```

这条路线适合 AI 研究、算法工程或模型训练岗位，但对应用开发者来说太慢，短期很难转化成产品能力。

更适合你的路线是：

```text
大模型认知
  -> API 调用
  -> Prompt
  -> 结构化输出
  -> Tool Calling
  -> RAG
  -> Agent
  -> Android / 后端 / 前端落地
  -> 评估与运维
```

这条路线能更快做出可运行的东西，也更贴近真实项目。

这条路线背后的原理顺序是：

```text
先理解模型怎么生成
再学会怎么调用模型
再学会怎么约束模型
再学会怎么给模型补资料
再学会怎么让模型调用真实系统
最后学会怎么评估和运维
```

如果顺序反过来，一开始就学 Agent 或微调，很容易遇到问题却不知道是哪一层出了错：是 Prompt 不清楚、上下文不够、检索不准、工具权限错、模型能力不足，还是评估方法不对。

## 2. 每个阶段应该达到什么效果

### 阶段一：基础认知

目标：

- 知道大模型是什么
- 知道大模型应用怎么分层
- 知道 Prompt、RAG、Agent、微调分别解决什么问题
- 知道 Android 端不应该直接暴露 API Key

能做的事：

- 画出一个大模型应用架构图
- 判断一个需求应该用 Prompt、RAG、工具调用还是微调

原理重点：

- 大模型是概率生成系统，不是确定性数据库。
- Token 和上下文窗口决定了一次请求能带多少信息。
- Prompt、RAG、工具调用和微调分别改变不同层面的能力。

边界判断：

- 不需要会训练模型。
- 不需要会推导 Transformer。
- 需要能说清“模型为什么可能答错，以及工程上怎么兜底”。

### 阶段二：API 基础

目标：

- 能从后端调用模型
- 能处理流式输出
- 能控制错误、超时、重试
- 能拿到结构化结果

能做的事：

- 写一个命令行聊天 Demo
- 写一个后端模型代理接口
- 写一个流式输出接口

原理重点：

- 理解一次模型请求里包含哪些信息：system、user、assistant、tools、参数、上下文。
- 理解流式输出不是模型一次性返回完整答案，而是边生成边传输。
- 理解超时、重试、限流、Token 成本是推理服务的一部分。

边界判断：

- API 调通只代表“能用”，不代表“可上线”。
- 真实产品还需要鉴权、日志、错误处理、成本统计和输出校验。

### 阶段三：Prompt Engineering

目标：

- 能写稳定的任务 Prompt
- 能控制输出格式
- 能让模型按角色、约束、步骤执行
- 能管理 Prompt 版本

能做的事：

- 写 Android 崩溃日志分析 Prompt
- 写代码 Review Prompt
- 写测试用例生成 Prompt

原理重点：

- Prompt 的作用是把模型的生成方向收窄。
- 角色、任务、约束、步骤、输出格式都会影响生成概率。
- 示例可以改变模型的模仿目标，但示例质量差也会把模型带偏。

边界判断：

- Prompt 不能创造模型完全没有的能力。
- Prompt 不能替代真实数据查询。
- Prompt 越长不一定越好，关键是清楚、相关、可执行。

### 阶段四：Function Calling

目标：

- 能把后端接口封装成工具
- 能让模型选择工具
- 能校验工具参数
- 能处理工具调用失败

能做的事：

- 让模型调用一个日志查询接口
- 让模型调用一个项目文件检索接口
- 让模型生成结构化工具参数

原理重点：

- 工具调用把“语言意图”连接到“真实系统能力”。
- 模型通常负责选择工具和生成参数，程序负责校验参数和执行工具。
- 工具返回结果会重新进入上下文，模型再基于结果继续回答。

边界判断：

- 工具不是给模型无限权限。
- 所有参数都要校验，所有高风险动作都要确认。
- 工具失败、超时、返回空结果时，也要设计模型下一步怎么处理。

### 阶段五：RAG

目标：

- 能把文档放入知识库
- 能根据问题检索相关内容
- 能让模型基于资料回答
- 能追踪答案来源

能做的事：

- 做一个项目文档问答系统
- 做一个 Android 业务知识库助手
- 做一个代码规范问答助手

原理重点：

- RAG 解决的是模型知识边界：训练时不知道、记不准、过期或私有的信息。
- Embedding 负责语义相似检索，分块和重排序决定模型看到哪些资料。
- 答案质量取决于“检索是否命中 + 上下文是否清楚 + Prompt 是否限制引用资料”。

边界判断：

- RAG 不是把文档丢进去就结束。
- 检索结果不相关时，模型可能照样编答案。
- 需要来源引用、置信度提示和无法回答时的兜底策略。

### 阶段六：Agent

目标：

- 能让模型执行多步骤任务
- 能控制任务边界
- 能记录每一步执行过程
- 能处理失败和人工确认

能做的事：

- 做一个自动分析 git diff 的代码 Review 助手
- 做一个自动读取日志、定位问题、生成建议的排查助手

原理重点：

- Agent 是“模型 + 工具 + 记忆/上下文 + 循环控制”的组合。
- 模型会根据当前观察结果决定下一步，而不是一次请求完成所有事。
- Agent 的关键不是让模型更自由，而是让它在可控边界内多步骤执行。

边界判断：

- 能不用 Agent 就先不用 Agent。
- 每个 Agent 都要有停止条件、工具白名单、日志和人工接管机制。
- 多步骤任务失败时，要能看清失败发生在哪一步。

### 阶段七：Android 落地

目标：

- 能在 Android 端展示流式结果
- 能接入语音输入和 TTS
- 能通过后端安全调用模型
- 能处理网络、延迟、隐私和耗电问题

能做的事：

- 做一个 Android 聊天助手
- 做一个语音大模型助手
- 做一个 App 崩溃日志智能分析入口

原理重点：

- Android 端主要处理交互、权限、端侧能力和状态展示。
- 模型推理、Prompt、RAG、工具权限通常应该由后端控制。
- 流式展示、取消生成、错误重试会直接影响用户对模型能力的感知。

边界判断：

- 不要在 App 里硬编码模型 API Key。
- 不要把敏感数据无提示地上传给模型服务。
- 不要假设移动网络稳定，必须处理超时、断线和恢复。

### 阶段八：评估与运维

目标：

- 能判断一次改动是否提升效果
- 能统计成本
- 能追踪失败案例
- 能做 Prompt / RAG / Agent 回归测试

能做的事：

- 建立 Prompt 测试集
- 建立 RAG 问答评估表
- 建立模型调用日志和 Trace

原理重点：

- 大模型输出有不确定性，所以需要用测试集和日志做持续比较。
- 每次 Prompt、模型、检索策略、工具逻辑变化，都可能影响结果。
- 评估不是只看“这次回答好不好”，而是看一组典型场景是否整体变好。

边界判断：

- 没有评估集，就很难证明一次优化真的有效。
- 没有 Trace，就很难定位失败来自模型、检索、工具还是业务上下文。
- 上线后必须关注成本、延迟、失败率和用户反馈。

## 3. 适合你的第一个实战项目

最适合从 Android 开发者背景切入的项目是：

```text
Android 崩溃日志智能分析工具
```

原因：

- 你熟悉 Android 日志和堆栈
- 输入数据容易准备
- 不需要一开始做复杂 UI
- 可以逐步引入 Prompt、RAG、Tool Calling、评估
- 成果容易迁移到真实项目

第一版可以非常简单：

```text
输入：崩溃日志 + 可选代码片段
输出：
  - 崩溃类型
  - 可能原因
  - 关键堆栈位置
  - 修复建议
  - 需要补充的信息
```

后续逐步升级：

```text
V1：纯 Prompt 分析
V2：加入结构化 JSON 输出
V3：接入项目文档 RAG
V4：接入 git diff 工具
V5：加入测试集评估
V6：做成 Android / Web 可视化工具
```

这个项目之所以适合作为第一实战，还因为它能把原理串起来：

- Token：崩溃日志可能很长，需要截取关键段落。
- 上下文窗口：不能把整个工程和所有日志都塞进去。
- Prompt：需要固定输出“异常类型、原因、位置、建议”。
- RAG：可以补项目文档、历史事故和代码规范。
- 工具调用：可以读取 git diff、文件片段、构建日志。
- 评估：可以积累真实 Crash Case，看分析是否稳定。

## 4. 学习时要避免的误区

### 误区一：把大模型当数据库

模型会生成答案，但它不是事实数据库。涉及真实业务数据时，应该通过数据库、知识库或工具查询。

### 误区二：什么都想靠微调解决

大多数应用问题先用 Prompt、RAG、工具调用解决。微调更适合稳定风格、固定任务模式或领域表达习惯。

### 误区三：只看 Demo，不做评估

大模型 Demo 很容易看起来有效，但上线后会遇到大量边界情况。必须建立测试集和日志回放能力。

### 误区四：Android 端直接调用模型 API

这样会暴露 API Key，也难以统一控制权限、成本、日志和 Prompt。推荐通过后端代理。

### 误区五：上下文越多越好

上下文太多会增加成本、延迟和干扰。应该把最相关的信息放进去。

### 误区六：参数调一调就能解决质量问题

temperature、top_p、max_tokens 只能影响生成方式，不能替代资料、Prompt、检索和校验。缺少事实时，参数再怎么调也只是让模型以不同方式猜。

### 误区七：Agent 越自动越高级

Agent 的价值在于受控地完成多步骤任务，不在于放开所有权限。没有日志、边界、停止条件和人工确认的 Agent，很容易变成难以排查的黑盒流程。

## 5. 本阶段学习检查清单

学完基础认知阶段后，你可以用下面问题检查自己：

- 我能不能解释训练和推理的区别？
- 我能不能解释 Token 和上下文窗口为什么重要？
- 我能不能说清 Prompt、RAG、工具调用、Agent 的区别？
- 我能不能画出 Android 大模型应用的推荐架构？
- 我能不能判断一个需求该不该用微调？
- 我能不能说出大模型应用上线后为什么需要评估和日志？
- 我能不能解释 API、Prompt、RAG、Tool Calling、Agent 每一步分别补的是什么能力？
- 我能不能说出一个 Android 大模型应用里哪些事情应该放端上，哪些应该放后端？

如果这些问题都能回答，说明可以进入下一阶段：大模型 API 基础。

## 6. 推荐的学习节奏

不要试图一次把所有概念学完。更适合开发者的节奏是“一个概念 + 一个小实验 + 一个边界问题”。

例如：

```text
学 Token
  -> 用同一段长日志试着压缩输入
  -> 思考哪些内容必须保留，哪些可以丢弃

学 Prompt
  -> 写一个崩溃日志分析模板
  -> 思考输出不稳定时是任务不清，还是资料不足

学 RAG
  -> 放入几篇项目文档做问答
  -> 思考检索错了时模型为什么会答错

学工具调用
  -> 让模型查询一个本地日志接口
  -> 思考参数校验和权限控制放在哪里
```

每学一层，都问自己三个问题：

- 这一层解决什么问题？
- 它解决不了什么问题？
- 失败时我怎么定位原因？

## 7. 本章小结

你的学习路线应该服务于工程落地，而不是先追求理论完整。

当前最重要的目标是：

```text
先能设计一个合理的大模型应用架构，
再逐步掌握 API、Prompt、RAG、Agent、Android 接入和评估运维。
```

下一阶段建议开始生成“大模型 API 基础”教程，并配一个最小可运行 Demo。
