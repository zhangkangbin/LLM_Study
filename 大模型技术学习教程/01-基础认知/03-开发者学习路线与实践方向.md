# 03. 开发者学习路线与实践方向

## 1. 不建议从传统机器学习路线开始

如果你的目标是做大模型应用，不建议一开始按下面路线学习：

```text
高等数学 -> 线性代数 -> 概率论 -> 传统机器学习算法 -> 深度学习框架 -> 从零训练模型
```

这条路线适合 AI 研究、算法工程或模型训练岗位，但对应用开发者来说太慢，短期很难转化成产品能力。

更适合 Android、后端、前端开发者的路线是：

```text
理解模型能力边界
  -> 安全调用模型 API
  -> 用 Prompt 和结构化输出约束模型
  -> 用 Embedding / RAG 补充私有知识
  -> 用工具调用和 Agent 连接真实系统
  -> 用后端网关、客户端状态机和多模态体验做产品闭环
  -> 用评估、运维、安全和团队流程支撑上线
```

这条路线背后的顺序是：

```text
先理解模型怎么生成
再学会怎么调用模型
再学会怎么约束模型
再学会怎么给模型补资料
再学会怎么让模型调用真实系统
最后学会怎么评估、运维和治理
```

如果顺序反过来，一开始就学 Agent、微调或私有化部署，很容易遇到问题却不知道是哪一层出了错：是 Prompt 不清楚、上下文不够、检索不准、工具权限错、模型能力不足，还是评估方法不对。

## 2. 21 个阶段应该怎么分组

这套教程现在是 21 个阶段，不再是简单的 8 个概念阶段。更建议按 6 个能力层来理解。

| 能力层 | 阶段 | 主要问题 |
| --- | --- | --- |
| 基础入口 | 01-02 | 大模型是什么，怎么通过后端安全调用，API 请求和上下文怎么组织 |
| 输出约束 | 03-05 | Prompt 怎么写，JSON/工具参数怎么稳定输出，模型和成本怎么选 |
| 知识增强 | 06-08 | 文档怎么变成可检索知识，Embedding、切分、索引、RAG、引用怎么配合 |
| 多步骤系统 | 09-10 | Agent 如何受控执行多步骤任务，后端网关如何承接模型、工具、限流和观测 |
| 产品落地 | 11-18 | 前端/Android/语音图片体验、评估测试、LLMOps、微调、私有化和安全怎么落地 |
| 团队和生态 | 19-21 | AI 编程流程、MCP/插件/协议边界，以及最终综合项目怎么串起来 |

学习时不要把每个阶段看成孤立知识点。它们更像同一个系统逐步增加能力：

```text
能问答
  -> 答得稳定
  -> 答得有依据
  -> 能调用工具
  -> 能在 Android / Web 里顺滑使用
  -> 能上线、监控、回滚和审计
```

## 3. 每个阶段应该达到什么效果

### 阶段 01：基础认知

目标：

- 知道大模型是概率生成系统，不是确定性数据库。
- 知道训练、推理、微调、量化、蒸馏分别是什么。
- 知道 Token、上下文窗口、幻觉、temperature、top_p 为什么重要。
- 能画出一个大模型应用的基本分层。

能做的事：

- 判断一个需求该用 Prompt、RAG、工具调用、Agent 还是微调。
- 解释为什么 Android 端不应该直接保存模型 API Key。

边界判断：

- 不需要会训练模型。
- 不需要推导 Transformer。
- 需要能说清“模型为什么可能答错，以及工程上怎么兜底”。

### 阶段 02：大模型 API 基础

目标：

- 能从后端调用模型。
- 能处理上下文、流式输出、错误、超时和重试。
- 能区分 Responses API、Chat Completions 和 OpenAI-compatible API。

能做的事：

- 写一个命令行聊天 Demo。
- 写一个后端模型代理接口。
- 给一次请求加 traceId、超时、错误码和日志。

边界判断：

- API 调通只代表“能用”，不代表“可上线”。
- 真实产品还需要鉴权、限流、日志、成本统计和输出校验。

### 阶段 03：Prompt Engineering

目标：

- 能写稳定的任务 Prompt。
- 能把角色、任务、约束、输入、输出格式和示例拆清楚。
- 能管理 Prompt 版本，并用测试保护 Prompt。

能做的事：

- 写 Android 崩溃日志分析 Prompt。
- 写代码 Review Prompt。
- 写测试用例生成 Prompt。

边界判断：

- Prompt 不能创造模型完全没有的能力。
- Prompt 不能替代真实数据查询。
- Prompt 越长不一定越好，关键是清楚、相关、可执行。

### 阶段 04：结构化输出与 Function Calling

目标：

- 能用 JSON Schema 约束输出。
- 能把后端接口封装成工具。
- 能校验工具参数，处理工具失败。

能做的事：

- 让模型输出可解析的崩溃分析 JSON。
- 让模型选择“查询日志”“搜索知识库”“创建工单”等受控工具。

边界判断：

- 模型生成工具参数，不代表参数可信。
- 工具执行前必须做 Schema、权限、预算和风险校验。

### 阶段 05：模型选型与成本评估

目标：

- 知道不同模型适合什么任务。
- 能估算输入 Token、输出 Token、工具调用、音频和检索成本。
- 能设计后端模型路由和降级策略。

能做的事：

- 给“崩溃分析、客服问答、语音助手、代码 Review”分别选模型。
- 建立每个用户、每个场景、每个租户的成本预算。

边界判断：

- 不要只看单次调用价格，还要看月活、并发、重试、缓存和失败成本。

### 阶段 06：Embedding 与向量检索

目标：

- 理解 Embedding 是把文本变成可比较的向量。
- 知道切分、索引、相似度、TopK 和过滤条件如何影响检索。
- 能区分自建向量库和托管 Vector Store / File Search。

能做的事：

- 用本地玩具向量检索 Demo 查找相似文档。
- 为 Android 崩溃手册、接口文档、代码规范设计切分策略。

边界判断：

- 向量相似不等于事实正确。
- 检索命中只是 RAG 的第一步，后面还要重排、组装上下文和引用。

### 阶段 07：数据工程与知识库构建

目标：

- 知道什么文档适合进入知识库。
- 能处理清洗、切分、元数据、版本、权限和增量同步。
- 能建立知识库构建流水线。

能做的事：

- 把项目 README、接口文档、崩溃排查手册整理成规范文档。
- 生成 chunks、manifest、sync plan。

边界判断：

- 数据质量差时，RAG 只会更稳定地返回差资料。
- 权限和版本必须在进入模型上下文前处理。

### 阶段 08：RAG 检索增强生成

目标：

- 能把检索结果组装进 Prompt。
- 能处理引用、兜底、权限和无法回答。
- 能判断问题出在检索、上下文、Prompt 还是模型。

能做的事：

- 做一个项目文档问答系统。
- 做一个 Android 业务知识库助手。
- 做一个代码规范问答助手。

边界判断：

- RAG 不是“把文档丢进去就结束”。
- 检索不到或检索错时，模型可能照样编答案，所以必须设计拒答和引用。

### 阶段 09：Agent 与多步骤任务

目标：

- 理解 Agent 是“模型 + 工具 + 状态 + 循环控制”。
- 能设计停止条件、工具白名单、人工确认和 Trace。
- 能区分单 Agent、多 Agent、专家工具和 handoff。

能做的事：

- 做一个自动读取日志、定位问题、生成建议的排查助手。
- 做一个自动分析 git diff 的代码 Review 助手。

边界判断：

- 能不用 Agent 就先不用 Agent。
- Agent 的价值不是“更自由”，而是在可控边界里完成多步骤任务。

### 阶段 10：大模型后端工程化

目标：

- 能设计 AI Gateway。
- 能处理模型路由、限流、重试、降级、流式响应、异步任务和观测。
- 能把供应商事件转换成业务客户端事件。

能做的事：

- 给 Android/Web 提供统一 `/api/chat`。
- 记录 requestId、userId、model、promptVersion、token、latency、errorCode。

边界判断：

- 客户端不应该直接承接模型供应商复杂度。
- Prompt、模型路由、工具权限和成本控制应该由后端统一管理。

### 阶段 11：前端与交互体验

目标：

- 能设计 AI 消息模型、流式状态机、取消、重试、引用展示和富文本渲染。
- 能处理多端体验差异。

能做的事：

- 做一个静态 Chat UI 状态机。
- 把 delta、引用、错误、完成事件映射成 UI 状态。

边界判断：

- 前端不要把模型输出当成可信 HTML 执行。
- 取消后仍可能收到迟到事件，状态机要能忽略。

### 阶段 12：Android 端接入大模型

目标：

- 能设计 Android 接入架构。
- 能处理网络流式输出、生命周期、ViewModel 状态、错误恢复和用户体验。

能做的事：

- 写 Android AI 客户端的 Repository、ViewModel、UI 状态骨架。
- 处理取消、重试、断网、迟到 delta 和引用展示。

边界判断：

- Android 端只保存业务登录态，不保存模型供应商 Key。
- 模型调用、RAG 权限、工具执行应该放后端。

### 阶段 13：语音与多模态能力

目标：

- 能区分 STT、TTS、普通语音链路和 Realtime 语音。
- 能处理图片输入、截图提问、多模态隐私和 Android 权限。

能做的事：

- 做“录音 -> 转写 -> 文本问答 -> 播报”的普通语音助手。
- 做截图提问或图片理解请求体。

边界判断：

- 只有需要低延迟、可打断、近似通话体验时，才优先考虑 Realtime。
- 图片和音频上传前必须让用户明确触发。

### 阶段 14：大模型评估与测试

目标：

- 能把“感觉不错”变成“有数据、有用例、有门禁”。
- 能设计规则打分、人工打分、模型打分和 Trace 打分。
- 能把评估接入 CI、发布和灰度。

能做的事：

- 建立 20 到 50 条高价值评估集。
- 给 Prompt、RAG、Agent 做回归评估。

边界判断：

- 单次人工试用不能证明质量。
- 没有基线版本，就很难知道一次改动是变好还是变差。

### 阶段 15：LLMOps 上线后的运维

目标：

- 能观测成本、延迟、错误率、拒答率、工具失败和用户反馈。
- 能设计灰度、告警、回滚和事故复盘。

能做的事：

- 建立模型调用日志和 Trace。
- 设置成本、延迟、错误率阈值。

边界判断：

- 上线不是结束，而是持续评估和治理的开始。

### 阶段 16：微调与模型定制

目标：

- 知道什么时候不该微调。
- 能准备训练/验证数据、质量检查和上线评估。
- 能区分 Prompt、RAG、微调和模型蒸馏的职责。

能做的事：

- 整理模型定制数据集。
- 判断一个需求应该先改 Prompt、加 RAG、做工具，还是考虑微调。

边界判断：

- 微调不适合更新事实知识。
- 微调会把数据质量问题固化进模型。

### 阶段 17：本地模型与私有化部署

目标：

- 能理解本地模型、私有网关、显存估算、并发、授权和可观测性。
- 能设计云边协同和本机小模型策略。

能做的事：

- 判断一个任务适合云端、本地、端侧还是混合路由。
- 给私有化环境设计网关、权限和审计。

边界判断：

- 本地模型不等于安全。
- 私有化部署仍然需要权限、日志、输出校验和红队测试。

### 阶段 18：大模型应用安全

目标：

- 能识别 Prompt 注入、数据泄露、越权工具调用和不可信输出。
- 能设计工具白名单、人工确认、输出校验和红队用例。

能做的事：

- 给知识库助手设计安全门禁。
- 给高风险工具加人工确认。

边界判断：

- 安全边界不能只靠 Prompt。
- 模型只能建议，系统负责决策，人类确认高风险动作。

### 阶段 19：AI 编程与研发效率提升

目标：

- 能把 AI 编程工具纳入稳定研发流程。
- 能写清任务说明、验收命令、边界和 Review 清单。
- 能沉淀 AGENTS、技能、模板和团队规范。

能做的事：

- 用 AI 辅助读代码、写测试、修 Bug、做 Review、写文档。
- 建立“AI 产出必须验证”的团队习惯。

边界判断：

- AI 可以提速，但验证必须落到命令、测试、截图或真实运行结果上。

### 阶段 20：生态与协议

目标：

- 能区分 API、SDK、OpenAPI、MCP、插件、App、Skill 和 Agent 工具。
- 能判断一个能力应该给普通系统调用，还是给 AI Host 调用。

能做的事：

- 给内部能力设计 OpenAPI。
- 给 AI 客户端设计 MCP Tool、Resource 和 Prompt。

边界判断：

- 协议不是业务架构本身。
- 核心业务能力应该独立于 MCP、插件或某个 Agent 框架。

### 阶段 21：综合实战项目

目标：

- 把前 20 个阶段串成一个 Android 知识库助手项目。
- 能写项目范围、架构、接口、数据、里程碑、验收、上线和扩展计划。

能做的事：

- 拆出 MVP、知识库增强、多模态体验、上线准备四个里程碑。
- 建立综合项目蓝图、验收清单和评估/安全/运维门禁。

边界判断：

- 第一版不要做成万能 AI 平台。
- 先做一个可运行、可测试、可观测、可回滚的闭环。

## 4. 适合你的第一个实战项目

最适合从 Android 开发者背景切入的项目是：

```text
Android 崩溃日志智能分析工具
```

原因：

- 你熟悉 Android 日志和堆栈。
- 输入数据容易准备。
- 不需要一开始做复杂 UI。
- 可以逐步引入 Prompt、结构化输出、RAG、工具调用、评估和安全。
- 成果容易迁移到真实项目。

第一版可以非常简单：

```text
输入：崩溃日志 + 可选代码片段
输出：
  - 崩溃类型
  - 可能原因
  - 关键堆栈位置
  - 修复建议
  - 需要补充的信息
```

后续逐步升级：

| 版本 | 新增能力 | 对应阶段 |
| --- | --- | --- |
| V1 | 纯 Prompt 分析 | 02-03 |
| V2 | 结构化 JSON 输出 | 04 |
| V3 | 模型成本估算和路由 | 05 |
| V4 | 项目文档 RAG 和引用 | 06-08 |
| V5 | git diff、构建日志、工单工具 | 09-10 |
| V6 | Android/Web 流式 UI | 11-12 |
| V7 | 语音输入和截图提问 | 13 |
| V8 | 评估集、监控、告警、安全红队 | 14-18 |
| V9 | 团队 AI 编程流程和协议扩展 | 19-20 |

这个项目之所以适合作为第一实战，还因为它能把原理串起来：

- Token：崩溃日志可能很长，需要截取关键段落。
- 上下文窗口：不能把整个工程和所有日志都塞进去。
- Prompt：需要固定输出“异常类型、原因、位置、建议”。
- 结构化输出：让程序能稳定解析和展示。
- RAG：可以补项目文档、历史事故和代码规范。
- 工具调用：可以读取 git diff、文件片段、构建日志。
- Agent：可以按“看日志 -> 查文档 -> 读 diff -> 生成建议”多步骤执行。
- 评估：可以积累真实 Crash Case，看分析是否稳定。
- 安全：不能泄露用户隐私、内部代码和 API Key。

## 5. 学习时要避免的误区

### 误区一：把大模型当数据库

模型会生成答案，但它不是事实数据库。涉及真实业务数据时，应该通过数据库、知识库或工具查询。

### 误区二：什么都想靠微调解决

大多数应用问题先用 Prompt、RAG、工具调用解决。微调更适合稳定风格、固定任务模式或领域表达习惯。

### 误区三：只看 Demo，不做评估

大模型 Demo 很容易看起来有效，但上线后会遇到大量边界情况。必须建立测试集和日志回放能力。

### 误区四：Android 端直接调用模型 API

这样会暴露 API Key，也难以统一控制权限、成本、日志和 Prompt。推荐通过后端代理。

### 误区五：上下文越多越好

上下文太多会增加成本、延迟和干扰。应该把最相关的信息放进去。

### 误区六：参数调一调就能解决质量问题

temperature、top_p、max_tokens 只能影响生成方式，不能替代资料、Prompt、检索和校验。缺少事实时，参数再怎么调也只是让模型以不同方式猜。

### 误区七：Agent 越自动越高级

Agent 的价值在于受控地完成多步骤任务，不在于放开所有权限。没有日志、边界、停止条件和人工确认的 Agent，很容易变成难以排查的黑盒流程。

### 误区八：私有化部署就天然安全

模型跑在公司服务器上，只是减少一部分数据出边界风险。权限、审计、Prompt 注入、工具越权、日志泄露仍然要处理。

### 误区九：AI 编程等于让模型直接改代码

AI 编程真正有价值的地方是：读代码、找影响面、写测试、做 Review、生成文档和辅助调试。改代码只是其中一步，而且必须验证。

## 6. 本阶段学习检查清单

学完基础认知阶段后，你可以用下面问题检查自己：

- 我能不能解释训练和推理的区别？
- 我能不能解释 Token 和上下文窗口为什么重要？
- 我能不能说清 Prompt、RAG、工具调用、Agent、微调的区别？
- 我能不能画出 Android 大模型应用的推荐架构？
- 我能不能判断一个需求该不该用微调？
- 我能不能说出大模型应用上线后为什么需要评估、日志和 Trace？
- 我能不能解释 API、Prompt、RAG、Tool Calling、Agent 每一步分别补的是什么能力？
- 我能不能说出 Android 大模型应用里哪些事情应该放端上，哪些应该放后端？
- 我能不能解释为什么本地模型和私有化部署仍然需要安全治理？
- 我能不能说出一个大模型项目从 Demo 到上线至少要补哪些门禁？

如果这些问题都能回答，说明可以进入下一阶段：大模型 API 基础。

## 7. 推荐的学习节奏

不要试图一次把所有概念学完。更适合开发者的节奏是“一个概念 + 一个小实验 + 一个边界问题”。

例如：

```text
学 Token
  -> 用同一段长日志试着压缩输入
  -> 思考哪些内容必须保留，哪些可以丢弃

学 Prompt
  -> 写一个崩溃日志分析模板
  -> 思考输出不稳定时是任务不清，还是资料不足

学 RAG
  -> 放入几篇项目文档做问答
  -> 思考检索错了时模型为什么会答错

学工具调用
  -> 让模型查询一个本地日志接口
  -> 思考参数校验和权限控制放在哪里

学评估
  -> 收集 20 条真实崩溃 Case
  -> 思考哪些输出必须命中，哪些错误必须阻断上线
```

每学一层，都问自己三个问题：

- 这一层解决什么问题？
- 它解决不了什么问题？
- 失败时我怎么定位原因？

## 8. 本章小结

你的学习路线应该服务于工程落地，而不是先追求理论完整。

当前最重要的目标是：

```text
先能设计一个合理的大模型应用架构，
再逐步掌握 API、Prompt、RAG、Agent、Android 接入、评估运维、安全和生态扩展。
```

下一阶段建议开始学习“大模型 API 基础”，并运行一个最小可用的 API 调用 Demo。
