# 04. 机器学习任务类型与开发者视角

## 1. 为什么要先分清任务类型

机器学习不是一种单一技术，而是一组“从数据里学习规律”的方法。对应用开发者来说，先不用背算法名字，先分清任务类型更重要。

因为任务类型决定后面的工程选择：

- 数据要怎么准备。
- 输出是什么形态。
- 用什么指标评估。
- 错误结果怎么处理。
- 能不能上线自动决策。

比如“判断一条评论是不是垃圾评论”和“预测下个月成本”不是一类问题；“给用户推荐文章”和“把一段语音转成文字”也不是一类问题。它们都可以用机器学习，但数据、指标、风险完全不同。

## 2. 监督学习：有标准答案的学习

监督学习是最容易理解的一类机器学习。

它的训练数据里有输入，也有标准答案。

```text
输入：一封邮件
标签：垃圾邮件 / 正常邮件

输入：一张商品图片
标签：鞋子 / 手机 / 食品

输入：房屋面积、位置、楼层
标签：成交价格
```

可以把监督学习理解成“带答案练题”。模型看很多题目和答案，学会从新题目里推断答案。

监督学习常见任务：

| 任务 | 输出 | 例子 |
| --- | --- | --- |
| 分类 | 离散类别 | 是否垃圾邮件、是否高风险用户 |
| 回归 | 连续数值 | 价格预测、耗时预测、成本预测 |
| 序列标注 | 每个位置一个标签 | 分词、命名实体识别 |
| 排序 | 一组结果的顺序 | 搜索结果排序、推荐排序 |

在大模型应用里，很多“看起来是 AI”的问题，本质上仍然可以拆成监督学习判断：

- 用户问题是否高风险。
- 模型输出是否包含敏感信息。
- 检索结果是否相关。
- 一个回答是否应该进入人工审核。

## 3. 无监督学习：没有标准答案时找结构

无监督学习的数据里没有人工标注答案。模型要从数据本身找规律。

常见例子：

1. 聚类：把相似用户或相似文档分组。
2. 降维：把复杂数据压缩成更容易观察的表示。
3. 异常检测：找出和多数样本明显不同的数据。
4. 主题发现：从大量文档里发现常见主题。

可以用一个开发场景理解：

```text
你有 10 万条用户反馈，但没人给它们分类。
你想先自动分成几组：
- 登录问题
- 支付问题
- 崩溃问题
- 功能建议
- 其他
```

这时候可以用聚类或 Embedding 相似度先做粗分，再让人给每组命名。

无监督学习适合探索数据结构，但它不会天然知道业务正确答案。聚出来的组是否有意义，仍然需要人和业务目标判断。

## 4. 半监督、自监督和大模型的关系

现实里，标注数据往往很贵。很多模型会利用没有人工标签的数据。

半监督学习是少量有标签数据加大量无标签数据。

自监督学习是从数据本身构造训练目标。例如语言模型训练时，可以用“根据上下文预测下一个 Token”作为训练任务。它不需要人工逐条标注答案，但仍然能从大量文本中学习语言规律。

大语言模型的预训练就可以粗略理解为一种大规模自监督学习：

```text
给模型看大量文本
让模型学习根据前文预测后面的 Token
模型逐渐学会语言、知识模式、代码结构和表达习惯
```

这也是为什么大模型能学到很多通用能力，但并不等于它能可靠回答所有事实问题。它学到的是数据里的模式，不是连接了你的实时数据库。

## 5. 强化学习：通过反馈学习策略

强化学习关注的是“智能体在环境中做动作，并根据奖励学习策略”。

可以用游戏理解：

```text
状态：当前棋盘
动作：下一步怎么走
奖励：赢了加分，输了扣分
目标：学会长期收益更高的策略
```

在大模型领域，你可能会听到“人类反馈强化学习”这类说法。它的大致直觉是：让模型生成多个回答，再根据人类偏好或奖励模型，引导模型更符合人类期望。

应用开发者不需要一开始实现强化学习，但要理解一个边界：

```text
模型经过偏好对齐后，更可能回答得有帮助、有礼貌、符合安全要求。
但它仍然可能事实错误，也仍然需要 RAG、工具、评估和权限控制。
```

## 6. 生成式任务：不只是分类和预测

传统机器学习里，很多任务是分类或预测。大模型更常见的是生成式任务：

- 生成回答。
- 总结文档。
- 改写文本。
- 生成代码。
- 生成结构化 JSON。
- 根据工具结果继续推理。

生成式任务更灵活，但也更难评估。

比如分类任务可以判断：

```text
预测：垃圾邮件
答案：垃圾邮件
结果：对
```

但生成式回答可能有很多合理版本。你不能只用字符串完全匹配判断好坏，而要看：

1. 是否事实正确。
2. 是否引用了正确来源。
3. 是否遵守输出格式。
4. 是否没有泄露敏感信息。
5. 是否对用户有帮助。

这就是为什么大模型应用需要评估集、规则打分、模型打分、人工抽检和线上反馈。

## 7. 开发者怎么判断任务类型

遇到一个 AI 需求，可以先问：

| 问题 | 如果答案是 |
| --- | --- |
| 是否有明确标准答案 | 监督学习、分类/回归/结构化输出更合适 |
| 是否只是想整理大量数据 | 聚类、Embedding、主题发现可能有用 |
| 是否需要生成自然语言 | 大模型生成式任务 |
| 是否需要查实时业务数据 | 工具调用或数据库查询 |
| 是否需要私有知识 | RAG |
| 是否需要多步骤操作 | Agent，但要加边界 |
| 是否涉及高风险动作 | 程序校验和人工确认 |

不要看到“智能”就默认上 Agent，也不要看到“回答不准”就默认微调。先把任务类型分清楚，后面的技术选择会简单很多。

## 8. Android 场景例子

以 Android 团队为例：

| 需求 | 任务类型 | 推荐方式 |
| --- | --- | --- |
| 判断崩溃日志属于哪类异常 | 分类 | 结构化输出或分类模型 |
| 预测一次模型调用成本 | 回归/规则估算 | 成本估算逻辑 |
| 根据崩溃日志生成排查建议 | 生成式任务 | Prompt + RAG |
| 找相似历史事故 | 语义检索 | Embedding + RAG |
| 自动创建排查工单 | 工具调用 | Function Calling + 人工确认 |
| 根据日志、文档、diff 多步排查 | 多步骤任务 | Agent |

这种拆法能避免一个常见误区：把所有能力都塞进一个 Prompt。工程上更稳的是，把不同任务拆成不同模块。

## 9. 完整例子：一个崩溃助手需求怎么拆

假设产品说：

```text
我想做一个 AI 功能，用户上传崩溃日志后，系统自动告诉他原因和修复建议。
```

这句话听起来像“让大模型回答一下”就行，但真正落地时至少能拆成 6 个小任务。

### 任务一：识别日志类型

输入：

```text
FATAL EXCEPTION: main
java.lang.NullPointerException
  at com.example.LoginActivity.onCreate(LoginActivity.kt:42)
```

输出：

```json
{
  "type": "crash",
  "exception": "NullPointerException"
}
```

这是分类任务。可以用规则、传统分类模型，也可以让大模型做结构化输出。它不需要 Agent。

### 任务二：判断日志是否足够

输入：

```text
App 崩了，帮我看看。
```

输出：

```json
{
  "enough_info": false,
  "missing": ["完整堆栈", "App 版本", "最近改动", "复现步骤"]
}
```

这也是分类或结构化判断。它的重点不是“生成漂亮回答”，而是判断能不能继续分析。

### 任务三：检索内部排查文档

用户问：

```text
LoginActivity 空指针怎么排查？
```

系统应该检索：

```text
Android 崩溃排查手册
登录模块常见问题
最近版本发布记录
```

这是语义检索和 RAG。它不是分类，也不是微调。关键是资料来源、权限和引用。

### 任务四：生成排查建议

输入：

```text
用户日志 + 检索到的文档片段 + 输出格式要求
```

输出：

```markdown
可能原因：
LoginActivity.onCreate 第 42 行对象未判空。

关键证据：
- NullPointerException
- main 线程
- LoginActivity.kt:42

建议：
1. 检查 intent extra 是否为空。
2. 检查登录态恢复逻辑。
3. 对可能为空的字段加保护。
```

这是生成式任务。大模型适合做这一步，但要有 RAG 和输出约束。

### 任务五：创建排查工单

输出建议后，用户点击“创建工单”。

工具参数：

```json
{
  "title": "LoginActivity 空指针崩溃",
  "severity": "P1",
  "module": "login",
  "evidence": ["crash_log_001", "android_crash_guide"]
}
```

这是工具调用。模型可以建议参数，但系统要校验权限，并让用户确认。

### 任务六：多步骤自动排查

如果系统自动执行：

```text
看日志 -> 查知识库 -> 读 git diff -> 查发布记录 -> 生成报告 -> 创建工单
```

这才进入 Agent 范畴。

这时必须有：

1. 工具白名单。
2. 停止条件。
3. Trace。
4. 权限检查。
5. 人工确认。

## 10. 反例：错误拆法

错误做法：

```text
把所有日志、全部文档、所有工具都塞给模型：
“你自己分析，必要时自己调用工具和创建工单。”
```

问题：

1. 模型可能关注错重点。
2. 无关文档会干扰回答。
3. 工具权限不可控。
4. 很难评估哪一步失败。
5. 安全风险高。

更稳的做法：

```text
先分类 -> 再判断信息是否足够 -> 再检索 -> 再生成 -> 再校验 -> 再由用户确认动作
```

这就是任务类型的价值：不是为了背概念，而是为了把一个模糊 AI 需求拆成可实现、可测试、可上线的模块。

## 11. 本章小结

机器学习任务类型决定工程方案。

对应用开发者来说，先掌握这几个判断就够了：

- 有标签答案：多半是监督学习。
- 没有标签但想找结构：多半是无监督学习。
- 生成文本、代码、总结：多半是生成式任务。
- 查实时数据：应该走工具或数据库。
- 查私有文档：应该走 RAG。
- 多步骤操作：才考虑 Agent。
