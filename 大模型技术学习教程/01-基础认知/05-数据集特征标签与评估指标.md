# 05. 数据集、特征、标签与评估指标

## 1. 数据决定模型能学到什么

机器学习里有一句很朴素的话：

```text
模型只能从数据中学习数据里存在的规律。
```

如果数据质量差、标签错、样本偏、字段缺失，再高级的模型也很难稳定工作。大模型也一样：Prompt、RAG、微调、评估集，本质上都离不开数据质量。

对应用开发者来说，理解数据集、特征、标签和指标，能帮你判断：

- 一个模型为什么答错。
- 一个评估集为什么不可信。
- 一个微调数据集为什么会把问题固化。
- 一个 RAG 知识库为什么检索效果差。

## 2. 数据集是什么

数据集是一组用于训练、验证、测试或评估的样本。

在普通机器学习里，一个样本可能长这样：

```json
{
  "text": "登录页点击验证码后闪退",
  "label": "crash"
}
```

在大模型应用评估里，一个样本可能长这样：

```json
{
  "id": "android-crash-001",
  "input": "空指针崩溃怎么排查？",
  "expected_source": "android_crash_guide",
  "required_keywords": ["FATAL EXCEPTION", "Caused by", "业务堆栈"],
  "forbidden_keywords": ["一定", "保证"]
}
```

两者形式不同，但目的类似：给系统一组典型任务，让你能判断输出是否满足预期。

## 3. 特征是什么

特征是模型用来做判断的输入信息。

传统机器学习里，特征通常是人工整理的字段：

```text
用户年龄、登录次数、最近一次购买时间、崩溃次数、设备型号
```

例如要判断一个请求是否异常，特征可能是：

| 特征 | 含义 |
| --- | --- |
| `request_count_1min` | 1 分钟内请求数 |
| `failed_login_count` | 登录失败次数 |
| `ip_risk_level` | IP 风险等级 |
| `device_changed` | 是否换设备 |

大模型时代，特征不一定是人工字段，也可能是文本、图片、音频或 Embedding。但工程直觉仍然一样：

```text
模型没有看到的信息，就不能稳定利用。
```

如果你让模型分析崩溃，但不给堆栈、版本、最近改动、设备信息，它只能根据常见模式猜。

## 4. 标签是什么

标签是训练时的“标准答案”。

分类任务标签可能是：

```text
crash / anr / network_error / permission_error
```

回归任务标签可能是：

```text
预计耗时：230 ms
预计成本：0.002 元
```

生成式任务也可以有参考答案，但通常不要求逐字一致：

```json
{
  "input": "帮我分析这段崩溃日志",
  "reference_answer": "这是 NullPointerException，关键证据是...",
  "must_include": ["NullPointerException", "LoginActivity", "判空"]
}
```

标签质量很关键。如果标签错，模型会学错；如果评估标签错，你会把好结果判坏，或者把坏结果判好。

## 5. 标注质量为什么重要

数据标注不是简单填字段。它要保证一致性。

例如崩溃分类里，有人把 `TimeoutException` 标成网络错误，有人标成后端错误，有人标成未知错误，模型就会学到混乱规则。

常见标注问题：

1. 标签定义不清楚。
2. 不同人标准不一致。
3. 样本太少，覆盖不了边界。
4. 只收集成功样本，缺少失败样本。
5. 标签里混入结果泄露。
6. 历史数据已经过期。

结果泄露是一个容易忽视的问题。例如你用“是否已退款成功”字段训练“是否应该退款”，模型可能只是学会看结果字段，而不是学会判断用户是否符合条件。

## 6. 评估指标是什么

评估指标是判断模型好坏的量化标准。

不同任务用不同指标。

分类任务常见指标：

| 指标 | 直觉 |
| --- | --- |
| Accuracy | 总体预测对了多少 |
| Precision | 预测为正的里面有多少是真的 |
| Recall | 真正为正的里面找回了多少 |
| F1 | Precision 和 Recall 的折中 |

用风控例子理解：

- Precision 低：系统误伤很多正常用户。
- Recall 低：系统漏掉很多风险用户。

不同业务取舍不同。安全场景可能更重 Recall，因为漏掉高风险很危险；用户体验场景可能更重 Precision，因为误伤会影响正常用户。

## 7. 大模型应用里的指标

大模型应用不能只看一个 Accuracy。

常见指标包括：

| 指标 | 解决什么问题 |
| --- | --- |
| 答案通过率 | 典型用例是否答对 |
| 引用准确率 | RAG 是否引用正确来源 |
| 拒答准确率 | 不知道时是否拒答 |
| JSON 解析成功率 | 结构化输出是否可用 |
| 工具调用正确率 | Agent 是否调用正确工具 |
| 越权率 | 是否阻止未授权工具或资料 |
| 成本 | 是否超预算 |
| 首 token 延迟 | 用户等待感 |
| 用户反馈 | 真实体验是否满意 |

这也是为什么大模型系统通常需要“多指标门禁”。

例如：

```json
{
  "min_answer_pass_rate": 0.85,
  "min_citation_accuracy": 0.8,
  "max_security_failures": 0,
  "max_latency_p95_ms": 5000,
  "max_cost_increase": 0.15
}
```

## 8. 数据集划分：训练、验证、测试

传统机器学习通常会把数据分成：

| 集合 | 用途 |
| --- | --- |
| 训练集 | 让模型学习 |
| 验证集 | 调参、选模型、选策略 |
| 测试集 | 最后评估泛化能力 |

在大模型应用里，也可以类比：

| 集合 | 大模型应用里的对应 |
| --- | --- |
| 开发样例 | 用来写 Prompt 和调 RAG |
| 回归评估集 | 每次改 Prompt/模型/RAG 都跑 |
| 隐藏测试集 | 发布前做更客观评估 |
| 线上反馈集 | 从真实失败案例持续补充 |

不要只用同一批样例反复调 Prompt，然后又用它证明效果好。这样很容易“对样例过拟合”。

## 9. Android 场景例子

假设你要做“Android 崩溃日志智能分析工具”。

样本可以这样设计：

```json
{
  "id": "crash-npe-001",
  "input": "FATAL EXCEPTION... NullPointerException at LoginActivity.kt:42",
  "expected_type": "NullPointerException",
  "expected_source": "android_crash_guide",
  "required_keywords": ["LoginActivity", "判空", "Caused by"],
  "forbidden_keywords": ["一定是后端问题"]
}
```

如果要做分类：

```json
{
  "features": {
    "exception_name": "NullPointerException",
    "thread": "main",
    "has_caused_by": true,
    "module": "login"
  },
  "label": "client_crash"
}
```

如果要做 RAG 评估：

```json
{
  "question": "启动页空指针闪退怎么排查？",
  "expected_doc_id": "android_crash_guide",
  "must_refuse_without_doc": true
}
```

同一个业务问题，可以拆成分类、检索、生成、评估多个层面。拆清楚后，系统更容易维护。

## 10. 好样本和坏样本对照

很多机器学习问题不是模型不行，而是样本写得太随意。

### 坏样本

```json
{
  "input": "App 崩了",
  "label": "bug"
}
```

问题：

1. 输入太短，没有堆栈。
2. 标签太泛，模型不知道是 Crash、ANR、网络错误还是权限问题。
3. 没有来源，也没有期望输出。
4. 无法用于评估回答质量。

### 好样本

```json
{
  "id": "crash-npe-login-001",
  "input": {
    "crash_log": "FATAL EXCEPTION: main\njava.lang.NullPointerException\nat LoginActivity.onCreate(LoginActivity.kt:42)",
    "app_version": "3.8.1",
    "recent_change": "登录页重构，新增自动填充手机号",
    "device": "Pixel 8 / Android 15"
  },
  "label": {
    "task_type": "crash_analysis",
    "exception_type": "NullPointerException",
    "module": "login",
    "severity": "P1"
  },
  "expected": {
    "required_keywords": ["LoginActivity.kt:42", "NullPointerException", "判空", "自动填充手机号"],
    "expected_source": "android_crash_guide",
    "forbidden_keywords": ["一定是后端问题"]
  }
}
```

这个样本更有价值，因为它能支持多个任务：

| 任务 | 使用哪些字段 |
| --- | --- |
| 崩溃分类 | `exception_type`、`module`、`severity` |
| RAG 检索评估 | `expected_source` |
| 生成式回答评估 | `required_keywords`、`forbidden_keywords` |
| 线上排查 | `app_version`、`recent_change`、`device` |

## 11. 指标选择例子：Precision 和 Recall 怎么取舍

假设你做一个“高风险输出拦截器”，判断模型回答是否可能泄露敏感信息。

场景一：内部测试环境。

```text
宁可多拦一点，也不能漏掉泄露。
```

这时更重 Recall。也就是所有真正危险的回答，要尽量找出来。

场景二：正式客服系统。

```text
不能把大量正常回答误拦，否则用户体验很差。
```

这时 Precision 也很重要。也就是被拦截的回答里，最好大多数真的有风险。

一个简单对照：

| 结果 | 含义 | 风险 |
| --- | --- | --- |
| 真阳性 | 危险回答被拦住 | 正确 |
| 假阳性 | 正常回答被拦住 | 用户体验下降 |
| 假阴性 | 危险回答没拦住 | 安全风险 |
| 真阴性 | 正常回答放行 | 正确 |

不同业务不是追求同一个指标最高，而是要先决定“哪种错误更不能接受”。

## 12. 小练习：给 5 条样本补字段

你可以拿下面 5 类问题做练习：

```text
1. 空指针崩溃
2. ANR
3. 接口 401
4. 图片上传失败
5. 用户要求导出其他团队文档
```

为每条样本补：

1. 输入字段。
2. 标签。
3. 必须命中的关键词。
4. 禁止出现的错误结论。
5. 期望引用来源。
6. 风险等级。

做完这个练习后，你会发现：真正难的不是“让模型回答”，而是把业务问题变成可学习、可评估、可回归的数据。

## 13. 本章小结

数据、特征、标签和指标，是机器学习和大模型应用的共同底座。

你需要记住：

- 数据决定模型能学什么。
- 特征决定模型能看见什么。
- 标签决定模型学什么答案。
- 指标决定你认为“好”是什么。
- 评估集决定你能不能证明系统真的变好了。

下一章会讲训练、验证、测试、过拟合和泛化，帮你理解为什么“在几个样例上表现好”不等于真的可靠。
