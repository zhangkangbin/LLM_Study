# 06. 训练、验证、测试、过拟合与泛化

## 1. 为什么 Demo 好用不等于能上线

做大模型应用时，经常会出现这种情况：

```text
试了 5 个问题，回答都不错。
上线后，真实用户一问就翻车。
```

传统机器学习里，这叫模型可能只在少量样本上表现好，但泛化能力不足。大模型应用也有类似问题：Prompt、RAG、工具、Agent 在几个手工样例上表现好，不代表它能覆盖真实复杂场景。

所以要理解三个概念：

- 训练。
- 验证。
- 测试。

以及两个风险：

- 过拟合。
- 泛化不足。

## 2. 训练集、验证集、测试集

在机器学习里，通常会把数据分开：

| 集合 | 用途 |
| --- | --- |
| 训练集 | 让模型学习规律 |
| 验证集 | 调整参数、选择模型、比较方案 |
| 测试集 | 最后评估真实效果 |

为什么不能都用同一批数据？

因为模型可能只是“记住了训练样本”，但遇到新样本就不会了。

这很像你刷题：

```text
只背 20 道原题 -> 原题考试很高分
换一套题 -> 可能不会
```

真正有用的是学会解题方法，而不是背答案。

## 3. 大模型应用里的对应关系

大模型应用不一定训练模型，但仍然需要类似划分。

| 机器学习概念 | 大模型应用里的对应 |
| --- | --- |
| 训练集 | 用来写 Prompt、整理 RAG、设计工具的开发样例 |
| 验证集 | 用来比较 Prompt 版本、检索策略、模型路由 |
| 测试集 | 发布前不轻易改动的回归评估集 |
| 线上数据 | 真实用户问题和失败反馈 |

例如你做崩溃分析助手：

1. 先用 10 条样例写第一版 Prompt。
2. 再用另外 20 条样例比较 Prompt V1 和 V2。
3. 发布前用固定 50 条回归集测试。
4. 上线后把失败案例补回评估集。

这样你才能知道改动是不是整体变好，而不是只把某几条样例调好了。

## 4. 什么是过拟合

过拟合是模型或策略在训练样本上表现很好，但遇到新样本表现差。

传统机器学习里的过拟合可能是：

```text
模型把训练数据里的噪声也学进去了。
```

大模型应用里的过拟合常见形式是：

1. Prompt 只适配了你手里的 3 条样例。
2. RAG 切分策略只对某几篇文档好用。
3. 评估规则只检查固定关键词，导致答案机械堆词。
4. Agent 只在演示路径里能跑通，真实工具失败就卡住。
5. 微调数据太少，模型学会了错误格式或偏见。

比如你为了让模型在样例中输出“NullPointerException”，把 Prompt 写成：

```text
请重点分析 NullPointerException。
```

结果遇到 ANR、OOM、网络错误时，它仍然硬往 NPE 上靠。这就是对样例过拟合的味道。

## 5. 什么是泛化

泛化是指系统在没见过的新样本上仍然表现可靠。

对大模型应用来说，泛化不是要求它“什么都会”，而是在目标范围内稳定：

```text
见过的崩溃类型能分析。
没见过但相似的崩溃能给合理排查方向。
资料不足时能拒答。
高风险动作不会乱执行。
```

泛化能力来自多个层面：

| 层面 | 对泛化的影响 |
| --- | --- |
| 模型能力 | 是否理解语言、代码、领域概念 |
| Prompt | 是否描述清楚任务和边界 |
| RAG | 是否能找到相关资料 |
| 工具 | 是否能查真实数据 |
| 评估集 | 是否覆盖典型和边界场景 |
| 安全策略 | 是否能阻止越界行为 |

## 6. 怎么降低过拟合

传统机器学习有很多技术手段，比如正则化、交叉验证、早停等。应用开发者可以先掌握工程侧做法：

1. 不要只用一两条样例调 Prompt。
2. 评估集覆盖正常、边界、失败、安全场景。
3. 把开发样例和发布评估集分开。
4. 每次改 Prompt、RAG、工具后跑同一组回归用例。
5. 不要为了单个失败样例把规则写得过死。
6. 记录失败归因：Prompt、检索、模型、工具、数据、权限。

对 RAG 来说，还要注意：

- 文档来源要稳定。
- chunk 不要太碎或太大。
- 权限过滤要在检索前。
- 无答案时允许拒答。

对 Agent 来说，还要注意：

- 工具有白名单。
- 每一步有停止条件。
- 工具失败有恢复策略。
- Trace 能回放。

## 7. 评估集覆盖什么

一个小但有用的评估集，应该覆盖：

| 类型 | 例子 |
| --- | --- |
| 高频问题 | 空指针、ANR、网络超时 |
| 边界问题 | 日志不完整、版本未知、堆栈被截断 |
| 无答案问题 | 知识库没有相关资料 |
| 权限问题 | 用户请求其他团队文档 |
| 安全问题 | Prompt 注入、要求泄露系统提示词 |
| 格式问题 | 输出必须是 JSON 或固定字段 |
| 工具问题 | 工具超时、返回空结果、参数非法 |

这样你才能看到系统在真实压力下的表现。

## 8. Android 崩溃分析例子

你可以把样例分成三组：

开发样例：

```text
5 条 NullPointerException
3 条 ANR
2 条网络错误
```

验证样例：

```text
不同模块、不同日志长度、不同 Android 版本
```

测试样例：

```text
线上真实失败案例，不随便拿来调 Prompt
```

每次改 Prompt 后，不要只看它是否修好了某一条 NPE，而要看：

1. ANR 有没有被误判成 NPE。
2. 无资料问题有没有拒答。
3. 引用来源是否正确。
4. JSON 是否还能解析。
5. 安全用例是否仍然通过。

## 9. 过拟合对照：Prompt 被一条样例带偏

假设你一开始只有这一条失败样例：

```text
问题：LoginActivity 空指针崩溃怎么排查？
正确方向：检查 intent extra、登录态恢复、手机号自动填充是否为空。
```

你为了修好它，把 Prompt 改成：

```text
遇到 Android 崩溃时，重点检查 intent extra、登录态和手机号自动填充。
```

这条样例可能变好了，但新问题会出现：

```text
问题：RecyclerView 滚动时 IndexOutOfBoundsException 怎么排查？
模型仍然回答：检查 intent extra、登录态和手机号自动填充。
```

这就是 Prompt 过拟合：为了一个样例，把规则写得太具体，导致其他场景被带偏。

更好的 Prompt 是：

```text
请先识别异常类型、线程、关键堆栈和模块。
只在证据指向登录模块时，才讨论 intent extra、登录态或手机号自动填充。
如果证据不足，请列出需要补充的信息。
```

这条 Prompt 更像通用排查流程，而不是硬编码某个答案。

## 10. 泛化对照：同类问题能不能迁移

下面三条是同类但不完全相同的问题：

```text
样例 A：LoginActivity.kt:42 NullPointerException
样例 B：ProfileFragment.kt:88 NullPointerException
样例 C：PaymentActivity.kt:103 lateinit property has not been initialized
```

泛化好的系统应该能做到：

| 样例 | 应该抓住的共同点 | 应该保留的差异 |
| --- | --- | --- |
| A | 都是空值相关崩溃 | 登录模块、intent extra |
| B | 都要看堆栈和生命周期 | 个人资料模块、Fragment 生命周期 |
| C | 都是初始化问题 | Kotlin lateinit 初始化顺序 |

如果系统只会背 A 的答案，说明泛化差。如果系统能提取“空值/初始化/生命周期”这类共性，再结合具体模块给建议，说明泛化更好。

## 11. 小数据集也有价值

你不一定一开始就有几千条样本。

对应用项目来说，20 到 50 条高质量用例就能显著提升稳定性。关键是这些用例要真实、有代表性、有边界。

第一版可以这样分：

```text
10 条正常问答
5 条无答案拒答
5 条权限/安全问题
5 条格式和结构化输出
5 条工具失败或边界情况
```

这比随手试 5 个问题可靠得多。

## 12. 小练习：给评估集分组

为崩溃分析助手准备 30 条样本，可以这样分：

| 分组 | 数量 | 例子 |
| --- | --- | --- |
| 正常崩溃分析 | 10 | NPE、IndexOutOfBounds、IllegalStateException |
| 非崩溃问题 | 5 | 网络错误、权限拒绝、后端 500 |
| 信息不足 | 5 | 只有“App 崩了”没有堆栈 |
| RAG 引用 | 5 | 必须引用内部排查手册 |
| 安全/权限 | 5 | 请求其他团队文档、要求泄露系统提示词 |

然后把它们分成：

```text
开发样例：10 条
验证样例：10 条
发布测试样例：10 条
```

规则是：不要用发布测试样例来反复调 Prompt。它要保留一点“考试题”的味道。

## 13. 本章小结

过拟合和泛化不是算法工程师才需要关心的概念。只要你在调 Prompt、调 RAG、调 Agent，你就会遇到它们。

记住这几句话：

- Demo 样例表现好，不等于真实场景可靠。
- 开发样例、验证样例、测试样例要分开。
- 不要为了单个样例把规则写死。
- 评估集要覆盖正常、边界、失败和安全场景。
- 上线后的失败案例要持续回流。
