# 07. 损失函数、梯度下降与优化直觉

## 1. 先建立一个直觉

训练模型不是程序员一条条写规则，而是让模型不断尝试、计算错误、调整参数。

可以把训练想成这样：

```text
模型给出预测
  -> 和标准答案比较
  -> 计算错得多严重
  -> 按错误方向调整内部参数
  -> 重复很多很多次
```

这里面有三个关键词：

- 损失函数。
- 梯度。
- 优化。

应用开发者不需要一开始推导公式，但理解这些直觉，能帮你明白模型为什么依赖数据、为什么会训练失败、为什么微调不是万能药。

## 2. 损失函数是什么

损失函数用来衡量模型这次预测错得有多严重。

例如分类任务：

```text
输入：一张图片
正确答案：猫
模型预测：狗
损失：较大
```

如果模型预测“猫”的概率很高，损失就小；如果预测“狗”的概率很高，损失就大。

回归任务也类似：

```text
真实耗时：200 ms
模型预测：210 ms
损失：小

真实耗时：200 ms
模型预测：2000 ms
损失：大
```

损失函数相当于训练过程里的“扣分规则”。扣分规则设计得好，模型才知道应该往哪个方向学。

## 3. 大语言模型里的损失直觉

大语言模型预训练时，经常可以粗略理解成预测下一个 Token。

```text
上下文：Android 应用发生 NullPointerException，应该先查看
目标下一个 Token：堆栈
```

模型会给词表里很多 Token 分配概率。如果正确 Token 的概率低，损失就高；如果正确 Token 的概率高，损失就低。

训练会不断推动模型提高正确 Token 的概率。

这也是为什么大模型很擅长生成连贯文本：它在海量文本上学过“什么上下文后面通常接什么内容”。

但这也带来一个边界：

```text
生成概率高，不等于事实一定正确。
```

很多听起来像真的句子，在语言模式上很合理，但事实可能是错的。所以事实问题仍然需要 RAG、工具和校验。

## 4. 梯度是什么

梯度可以粗略理解为：告诉模型参数应该往哪个方向调整，才能让损失变小。

想象你站在一座山上，目标是走到山谷最低点。你不知道全图，只能感受当前位置哪个方向更低。

```text
当前位置 -> 计算坡度 -> 朝下降方向走一点 -> 再计算 -> 再走一点
```

梯度就是这个“下降方向”的信息。

模型有大量参数。训练时，系统会根据损失计算每个参数应该怎么调整，让下一次预测更接近答案。

## 5. 梯度下降是什么

梯度下降是一种优化方法：沿着让损失变小的方向更新参数。

简化理解：

```text
参数 = 参数 - 学习率 * 梯度
```

学习率可以理解为每一步走多大。

- 学习率太小：走得很慢，训练成本高。
- 学习率太大：可能越过最低点，甚至训练不稳定。

这和调系统参数有点像：步子太小效率低，步子太大容易抖。

## 6. 优化不是保证找到完美答案

训练目标通常是让总体损失尽量低，但不保证模型学到人类真正想要的一切。

原因包括：

1. 数据有噪声。
2. 标签有错误。
3. 模型容量有限。
4. 训练目标和真实业务目标不完全一致。
5. 优化可能停在局部较好的区域。
6. 评估指标没有覆盖真实风险。

比如模型在训练中学会了“写得像答案”，但业务真正要的是“事实正确、可追溯、可执行”。这两个目标不完全一样。

所以大模型应用要在模型外再加：

- 引用来源。
- 输出校验。
- 工具查询。
- 安全策略。
- 人工确认。
- 评估门禁。

## 7. 为什么数据规模和质量都重要

模型通过损失函数从数据中学习。如果数据覆盖不足，模型就很难学到对应规律。

如果训练数据里很少有 Android 崩溃日志，模型对这类日志的理解就可能不稳定。

如果数据里有大量错误示例，模型可能学到错误模式。

如果微调数据里所有答案都很啰嗦，模型可能学会啰嗦。

如果评估集只检查“有没有关键词”，模型可能学会堆关键词，而不是解决问题。

所以数据质量和评价方式会直接影响最终行为。

## 8. 微调为什么要谨慎

微调会继续训练模型参数。它不是“给模型临时补资料”，而是在改变模型长期行为。

这意味着：

1. 错误数据会被学进去。
2. 过期知识可能被固化。
3. 标注风格会影响输出风格。
4. 数据偏见会影响模型偏好。
5. 评估不足时，很难知道有没有副作用。

如果你的问题是“知识库资料更新了”，优先用 RAG。

如果你的问题是“需要查实时订单状态”，优先用工具调用。

如果你的问题是“输出格式不稳定”，优先用结构化输出。

只有当任务模式稳定、数据质量高、评估闭环清楚时，才认真考虑微调。

## 9. 应用开发者需要掌握到什么程度

你不需要手写反向传播，但要有这些判断：

| 现象 | 可能原因 |
| --- | --- |
| 模型某类任务总是做不好 | 训练数据或模型能力边界不足 |
| 少数样例调好了，其他变差 | Prompt 或微调数据过拟合 |
| 模型答案像真的但不准确 | 生成目标不等于事实校验 |
| 微调后风格变了但事实仍错 | 微调不适合更新动态知识 |
| 评估分提高但用户不满意 | 指标没有覆盖真实体验 |

这些判断能帮你少走弯路。

## 10. Android 场景例子

假设你想让模型更好地分析崩溃日志。

不要直接想“我要训练一个模型”。先问：

1. 是不是 Prompt 没说清输出字段？
2. 是不是没有提供堆栈、版本、最近改动？
3. 是不是 RAG 没找到内部排查文档？
4. 是不是工具没有查到 git diff 或发布记录？
5. 是不是评估集太少，导致你误判质量？
6. 是不是模型本身确实不擅长代码和日志？

如果前五个都做好了，仍然在固定类型日志上不稳定，再考虑微调或换模型。

## 11. 数字小例子：损失不是“错/对”这么简单

假设你训练一个简单分类器，判断日志类型：

```text
类别：crash / anr / network_error
真实答案：crash
```

模型 A 输出概率：

```json
{
  "crash": 0.80,
  "anr": 0.15,
  "network_error": 0.05
}
```

模型 B 输出概率：

```json
{
  "crash": 0.34,
  "anr": 0.33,
  "network_error": 0.33
}
```

两个模型最后都可能预测 `crash`，但模型 A 更确定，损失更小；模型 B 只是勉强猜中，损失更大。

再看模型 C：

```json
{
  "crash": 0.05,
  "anr": 0.90,
  "network_error": 0.05
}
```

模型 C 不只是错，而且非常自信地错，损失会更大。

这能帮助你理解：训练不只是看最终类别对不对，还会看模型对正确答案的概率是否足够高。

## 12. 生成式例子：为什么答案像真的也可能损失低

语言模型训练时，目标常常是预测下一个 Token。

上下文：

```text
FATAL EXCEPTION: main
java.lang.NullPointerException
at LoginActivity.onCreate
这个问题优先检查
```

训练数据里的后续文本可能是：

```text
空对象访问和初始化顺序。
```

模型学到的是：

```text
在这种上下文后，“空对象”“初始化”“判空”这些 Token 概率应该更高。
```

这很有用，但也解释了幻觉风险：如果上下文里缺少真实代码，模型仍然可能生成“初始化顺序”这类常见但未必真实的解释。

所以在应用里要补：

1. 真实堆栈。
2. 相关代码片段。
3. RAG 文档。
4. 输出中的“不确定”选项。
5. 程序校验和人工确认。

## 13. 梯度下降类比：调一个登录页超时阈值

假设你不是训练模型，而是在手动调一个登录接口超时阈值。

```text
阈值太短：弱网用户经常失败。
阈值太长：真正失败时用户等太久。
```

你会观察错误率和等待时间，然后一点点调整阈值。

梯度下降也是类似思路，只是模型参数不是一个超时阈值，而是海量数字；调整方向不是人凭经验判断，而是通过损失函数和梯度计算出来。

这个类比不完全严谨，但能建立直觉：

```text
损失函数告诉你现在有多差。
梯度告诉你往哪个方向调。
学习率决定每次调多少。
```

## 14. 本章小结

损失函数、梯度下降和优化的核心直觉是：

```text
模型通过数据里的错误反馈，不断调整参数，让总体预测更接近训练目标。
```

但训练目标不等于业务目标。大模型应用要把模型能力放进工程系统里，用上下文、工具、RAG、评估、安全和人工确认补齐边界。

下一章会讲传统机器学习、深度学习和大模型之间的演进关系，帮你理解为什么大模型不是凭空出现的。
