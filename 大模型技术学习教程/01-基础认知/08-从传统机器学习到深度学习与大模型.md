# 08. 从传统机器学习到深度学习与大模型

## 1. 为什么要理解这条演进线

很多大模型概念听起来像全新的东西，但它们并不是凭空出现的。

从传统机器学习到深度学习，再到大模型，核心变化可以粗略理解为：

```text
人工设计特征
  -> 模型自动学习特征
  -> 大模型学习通用表示和生成能力
```

理解这条线，可以帮你判断：

- 什么时候简单规则或传统模型就够了。
- 什么时候需要深度学习。
- 什么时候适合大模型。
- 为什么大模型仍然需要数据、评估和工程边界。

## 2. 传统机器学习：人设计特征，模型学规则

传统机器学习通常需要人把原始数据整理成特征。

例如判断用户是否可能流失：

```text
最近 7 天打开次数
最近一次登录时间
是否购买过
客服投诉次数
设备类型
```

模型根据这些字段学习规律。

常见传统机器学习方法包括：

- 线性回归。
- 逻辑回归。
- 决策树。
- 随机森林。
- 梯度提升树。
- 支持向量机。
- 朴素贝叶斯。

你不需要马上掌握每个算法细节，但要知道它们适合很多结构化数据任务，比如风控、推荐粗排、预测、分类、异常检测。

传统机器学习的优点：

1. 训练成本相对低。
2. 可解释性通常更好。
3. 对结构化数据很强。
4. 部署和推理成本低。

缺点：

1. 很依赖人工特征。
2. 处理文本、图片、语音时能力有限。
3. 很难直接做开放式生成。

## 3. 深度学习：模型自己学表示

深度学习用多层神经网络从数据中学习表示。

在图像任务中，模型可以从像素中逐层学到：

```text
边缘 -> 纹理 -> 局部形状 -> 物体结构
```

在文本任务中，模型可以从 Token 中学到：

```text
词形 -> 语法 -> 语义 -> 上下文关系
```

深度学习减少了大量人工特征工程，尤其适合图像、语音、自然语言这类复杂数据。

但它也带来新的成本：

1. 需要更多数据。
2. 需要更多算力。
3. 可解释性更弱。
4. 调试更依赖评估和可观测性。

## 4. 大模型：通用能力和生成能力

大模型通常有大量参数，在海量数据上训练，具备更强的通用能力。

大语言模型最典型的能力是：

1. 理解自然语言指令。
2. 生成文本。
3. 总结、改写、翻译。
4. 生成代码。
5. 根据上下文做推理。
6. 结合工具完成任务。

和传统模型相比，大模型的输入更自由，输出也更自由。

传统模型可能是：

```text
输入字段 -> 输出类别
```

大模型可以是：

```text
用户问题 + 文档 + 工具结果 + 输出要求 -> 生成回答
```

这种灵活性很强，但也意味着工程上必须控制边界。

## 5. 三者不是替代关系

不要以为有了大模型，传统机器学习和规则就没用了。

在真实系统里，三者经常共存：

| 场景 | 更合适的方式 |
| --- | --- |
| 精确权限判断 | 规则/业务系统 |
| 订单状态查询 | 数据库/API |
| 风险评分 | 传统机器学习或规则模型 |
| 图片识别 | 深度学习视觉模型 |
| 文档问答 | RAG + 大模型 |
| 文本总结 | 大模型 |
| 多步骤排查 | Agent + 工具 + 大模型 |

大模型不是替代所有系统，而是新增了一层自然语言和推理接口。

## 6. 从规则到模型再到大模型的例子

以 Android 崩溃分析为例。

规则方式：

```text
如果日志包含 "NullPointerException" -> 分类为 NPE
如果日志包含 "ANR" -> 分类为 ANR
```

传统机器学习方式：

```text
提取异常名、线程、模块、堆栈深度、版本等特征
训练分类模型判断崩溃类型
```

深度学习方式：

```text
把日志文本输入模型
模型学习日志中的模式并分类
```

大模型方式：

```text
输入崩溃日志 + 项目文档 + 最近改动 + 输出格式
模型生成：
- 崩溃类型
- 关键证据
- 可能原因
- 修复建议
- 需要补充的信息
```

Agent 方式：

```text
模型先看日志
再调用知识库检索
再读取 git diff
再生成排查报告
必要时创建工单
```

越往后越灵活，但也越需要权限、评估、日志和人工确认。

## 7. 什么时候不用大模型

这些场景不一定需要大模型：

1. 规则明确、输出固定。
2. 需要毫秒级延迟。
3. 成本极敏感。
4. 结果必须完全可解释。
5. 输入输出都是结构化字段。
6. 用 SQL 或普通代码就能稳定解决。

例如：

```text
用户是否有权限访问文档
订单是否已支付
金额是否超过阈值
接口是否返回 200
```

这些应该由业务系统决定，而不是交给大模型猜。

## 8. 什么时候大模型很有价值

大模型特别适合：

1. 输入是自然语言、代码、日志、文档。
2. 用户问题表达方式很多。
3. 输出需要解释、总结、建议。
4. 需要把多个上下文组合起来。
5. 需要生成候选方案。
6. 需要和工具、知识库配合。

例如：

```text
把一段崩溃日志转成排查建议
总结一篇事故复盘
根据项目文档回答新人问题
把用户描述改写成工单标题和步骤
根据 diff 做代码 Review
```

## 9. 大模型应用的组合思路

一个稳定的大模型应用，通常不是“一个模型搞定全部”，而是组合：

```text
规则系统：权限、限流、风险门禁
数据库/API：真实业务数据
Embedding/RAG：私有知识
大模型：理解、总结、生成、推理
工具调用：连接真实系统
评估集：验证质量
LLMOps：监控成本、延迟、失败
人工确认：高风险动作兜底
```

这也是本教程后续 21 个阶段的主线。

## 10. 完整选型例子：同一个功能的五种实现

需求：

```text
用户上传一段崩溃日志，系统给出排查建议。
```

### 方案一：纯规则

```text
如果包含 NullPointerException -> 输出 NPE 排查模板
如果包含 ANR -> 输出 ANR 排查模板
```

适合：

- 异常类型很少。
- 输出模板固定。
- 不需要解释复杂上下文。

问题：

- 遇到新异常容易漏。
- 无法结合业务上下文。
- 输出很机械。

### 方案二：传统机器学习分类

输入特征：

```json
{
  "exception_name": "NullPointerException",
  "thread": "main",
  "stack_depth": 18,
  "module": "login",
  "has_caused_by": true
}
```

输出：

```json
{
  "category": "client_crash",
  "severity": "P1"
}
```

适合：

- 做类型判断。
- 做风险等级预测。
- 数据结构清楚，有标签。

问题：

- 很难直接生成自然语言排查建议。
- 需要人工设计特征。

### 方案三：深度学习文本分类

输入整段日志，模型直接判断类型。

适合：

- 日志文本变化大。
- 人工特征难设计。
- 有足够标注样本。

问题：

- 可解释性弱。
- 仍然不擅长查内部最新文档。

### 方案四：大模型 + RAG

输入：

```text
崩溃日志 + 检索到的内部排查文档 + 输出格式要求
```

输出：

```text
关键证据、可能原因、排查步骤、引用来源、需要补充的信息
```

适合：

- 需要自然语言解释。
- 需要结合内部文档。
- 用户问题表达多样。

问题：

- 需要检索、引用、拒答和评估。
- 成本和延迟更高。

### 方案五：Agent + 工具

步骤：

```text
看日志 -> 查 RAG -> 查 git diff -> 查发布记录 -> 生成报告 -> 创建工单
```

适合：

- 需要多步骤排查。
- 需要调用真实系统。
- 需要输出可执行行动。

问题：

- 权限和安全复杂。
- 需要 Trace、停止条件和人工确认。
- 更难测试。

## 11. 怎么选择

可以按这个顺序判断：

```text
规则能稳定解决吗？
  能 -> 用规则
不能 -> 是否是结构化预测？
  是 -> 考虑传统机器学习
不是 -> 是否需要理解文本/图片/语音？
  是 -> 考虑深度学习或大模型
是否需要私有知识？
  是 -> 加 RAG
是否需要执行动作？
  是 -> 加工具调用
是否需要多步骤自主执行？
  是 -> 再考虑 Agent
```

这条顺序能帮你避免过度设计。大模型很强，但不是每个按钮、每个判断、每个接口都需要大模型。

## 12. 本章小结

传统机器学习、深度学习和大模型是一条演进线，但不是简单替代关系。

你可以这样记：

- 规则适合明确边界。
- 传统机器学习适合结构化预测。
- 深度学习适合复杂感知和表示学习。
- 大模型适合语言、知识、生成和工具协作。
- 真实产品通常是它们的组合。

学完这些机器学习基础后，再学习 API、Prompt、RAG、Agent，就不会只是在记名词，而能理解每一层为什么存在。
