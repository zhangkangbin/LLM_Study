# 02. 请求、响应与上下文管理

## 1. 为什么请求结构很重要

大模型 API 的输出质量，很大程度取决于你如何组织输入。

普通后端接口通常是：

```text
字段正确 -> 逻辑执行 -> 返回确定结果
```

大模型 API 更像：

```text
任务描述 + 背景信息 + 约束条件 + 输出格式 -> 生成结果
```

如果请求结构混乱，模型就会出现：

- 答非所问
- 输出格式不稳定
- 忽略关键约束
- 把示例当真实数据
- 编造不存在的信息

## 2. `instructions` 和 `input`

可以先这样区分：

| 字段 | 类似概念 | 放什么 |
| --- | --- | --- |
| `instructions` | System Prompt | 角色、任务原则、输出约束 |
| `input` | User Prompt | 用户本次具体问题或数据 |

示例：

```json
{
  "model": "gpt-5.5",
  "instructions": "你是 Android 稳定性分析助手。回答必须包含：问题类型、关键堆栈、可能原因、修复建议。",
  "input": "请分析这个崩溃日志：java.lang.NullPointerException ..."
}
```

建议：

- 稳定规则放 `instructions`。
- 每次变化的数据放 `input`。
- 不要把所有内容都堆在一个长字符串里。
- 如果后续要做缓存，稳定内容放前面，动态内容放后面。

## 3. 上下文不是越多越好

上下文包括：

- 用户问题
- 历史对话
- 系统指令
- 文档片段
- 代码片段
- 日志
- 工具返回结果

上下文过多会带来问题：

- 成本上升
- 延迟上升
- 关键信息被稀释
- 无关信息干扰模型判断

实际工程里应该先过滤，再输入。

例如分析 Android 崩溃，不要一次塞完整日志文件。优先提取：

- 异常类型
- 崩溃线程
- 关键堆栈
- caused by 链
- 相关业务日志
- 版本号、设备信息、系统版本

## 4. 响应结构如何理解

模型响应不是永远只有一段字符串。

Responses API 可能返回一个 `output` 列表，每个元素可能是消息、工具调用、推理事件或其他类型。

对基础文本生成来说，你最关心的是文本内容：

```json
{
  "output": [
    {
      "type": "message",
      "content": [
        {
          "type": "output_text",
          "text": "这里是模型生成的结果"
        }
      ]
    }
  ]
}
```

在真实项目中，建议后端把模型原始响应转换成业务稳定格式：

```json
{
  "answer": "这里是模型生成的结果",
  "trace_id": "trace_20260709_001",
  "model": "gpt-5.5",
  "finish_reason": "completed"
}
```

这样 Android 和前端不用关心模型供应商的内部结构。

## 5. 上下文管理的三种方式

### 方式一：客户端传完整历史

每次请求都传完整对话历史。

优点：

- 实现简单。
- 后端无状态。

缺点：

- Token 成本越来越高。
- 客户端容易篡改历史。
- 隐私和日志管理困难。

### 方式二：后端保存会话

后端保存历史消息，每次根据会话 ID 取上下文。

优点：

- 安全可控。
- 便于日志追踪。
- 便于做上下文裁剪。

缺点：

- 后端需要维护会话存储。

### 方式三：模型侧状态

某些 API 支持用上一次响应 ID 继续会话。

优点：

- 减少重复传输。
- 适合多轮任务。

缺点：

- 和供应商能力绑定更强。
- 对数据留存和合规要求更敏感。

学习阶段建议先用方式二：后端保存会话，自己控制上下文。

## 6. Android 场景示例：崩溃日志分析请求

后端可以把 Android 上传的数据整理成这种结构：

```json
{
  "instructions": "你是 Android 崩溃分析助手。请只基于输入日志分析，不要编造项目代码。",
  "input": {
    "task": "分析崩溃原因",
    "app_version": "1.8.2",
    "android_version": "14",
    "device": "Pixel 8",
    "exception": "java.lang.NullPointerException",
    "stacktrace": "...",
    "recent_changes": "登录页重构，增加缓存读取"
  }
}
```

如果 API 的 `input` 暂时只传字符串，也可以在后端拼成清晰文本：

```text
任务：分析 Android 崩溃原因
约束：只基于提供的信息，不确定时说明需要更多上下文

App 版本：1.8.2
Android 版本：14
设备：Pixel 8
异常类型：java.lang.NullPointerException
关键堆栈：
...
最近改动：
登录页重构，增加缓存读取
```

## 7. 请求设计检查清单

每次设计模型请求时，检查这几个问题：

- 模型知道自己扮演什么角色吗？
- 模型知道这次任务的目标吗？
- 输入里有没有无关信息？
- 输出格式有没有明确要求？
- 不确定时是否允许它说“不确定”？
- 有没有敏感信息需要脱敏？
- 有没有必要记录 trace ID 方便排查？

## 8. 本章小结

API 调用不是简单地把用户输入转发给模型。真正的工程能力在于：

```text
把业务问题整理成模型容易理解、容易验证、容易追踪的请求结构。
```
