# 01. Prompt Engineering 基础

## 1. Prompt 是什么

Prompt 是你提供给模型的输入和指令。它不仅包括用户问题，也包括系统规则、角色、背景资料、示例、输出格式和约束条件。

一个大模型应用里，Prompt 常常决定了模型能不能稳定完成任务。

例如同样分析 Android 崩溃：

```text
帮我看看这个崩溃。
```

和：

```text
你是 Android 稳定性分析助手。
请只基于输入日志分析，不要编造项目代码。
输出必须包含：问题类型、关键证据、可能原因、修复建议、需要补充的信息。
```

效果会很不一样。

## 2. Prompt Engineering 不是玄学

Prompt Engineering 容易被误解成“找一句神奇提示词”。实际工程里，它更接近接口设计。

你需要定义：

- 模型扮演什么角色。
- 模型要完成什么任务。
- 哪些信息可信，哪些只是用户输入。
- 输出给谁看。
- 输出格式是否固定。
- 不确定时该怎么办。
- 哪些内容不能做。

这和你设计后端接口、Android ViewModel 状态、前端组件 Props 很像。输入边界越清楚，输出越稳定。

## 3. `instructions` 和 `input` 的分工

在 Responses API 里，可以先按这个分工理解：

| 部分 | 放什么 | 变化频率 |
| --- | --- | --- |
| `instructions` | 角色、规则、输出要求、示例 | 相对稳定 |
| `input` | 用户本次问题、日志、业务数据 | 每次变化 |

示例：

```json
{
  "instructions": "你是 Android 稳定性分析助手。只基于输入日志分析，不要编造项目代码。",
  "input": "请分析下面的崩溃日志：java.lang.NullPointerException ..."
}
```

稳定规则放 `instructions`，动态数据放 `input`。这样做的好处是：

- 便于复用。
- 便于测试。
- 便于版本管理。
- 便于后续做 Prompt 缓存和成本优化。

## 4. Prompt 的常见组成

一个工程化 Prompt 通常包括：

```text
身份 Identity
任务目标 Goal
输入说明 Input
约束 Rules
输出格式 Output
不确定处理 Fallback
示例 Examples
```

不一定每个 Prompt 都要很长。简单任务用简单 Prompt，复杂任务才需要更多结构。

## 5. 为什么要写“不确定时怎么办”

大模型倾向于给出看起来完整的答案。如果输入信息不足，而 Prompt 没有允许它说“不确定”，它就更容易补全、猜测甚至编造。

例如：

```text
如果无法根据输入日志确认根因，请明确回答“不确定”，并列出需要补充的日志或代码。
```

这类规则非常重要，尤其适合：

- 崩溃分析
- 医疗、法律、金融等高风险领域
- 企业内部知识库问答
- 代码审查
- 自动化工具调用

## 6. 少写“思考过程”，多写“成功标准”

很多旧 Prompt 会写：

```text
请一步一步思考。
```

现在更推荐写清楚结果要求，而不是强迫模型输出思考链。

更好的方式：

```text
请给出结论、证据、风险和下一步操作。
如果证据不足，说明缺少什么信息。
```

对应用开发来说，用户需要的是可执行结果，不是模型的完整内部推理过程。

## 7. Prompt 和普通代码的相似点

Prompt 应该像代码一样管理：

- 有文件名。
- 有版本。
- 有评审。
- 有测试用例。
- 有变更记录。
- 有线上效果监控。

不要把重要 Prompt 散落在代码各处，也不要让 Android、前端、后端各自偷偷维护一份不同 Prompt。

## 8. 本章小结

Prompt Engineering 的核心是：

```text
把模糊的自然语言需求，整理成模型可执行、系统可维护、结果可验证的任务说明。
```
