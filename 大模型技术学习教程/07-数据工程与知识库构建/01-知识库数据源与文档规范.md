# 知识库数据源与文档规范

知识库建设的第一步不是选向量数据库，而是确认“哪些内容值得进入知识库”。大模型不会自动把混乱资料变清晰，它只会更快地暴露资料里的混乱。

## 常见数据源

对一个已有 Android、后端、前端项目来说，可以从这些数据开始：

| 数据源 | 适合放入知识库的内容 | 注意点 |
| --- | --- | --- |
| 产品文档 | 功能说明、业务规则、FAQ | 要标注版本和适用端 |
| 接口文档 | URL、参数、错误码、鉴权规则 | 避免泄露密钥和内部地址 |
| 崩溃与 ANR 经验 | 异常类型、堆栈特征、排查路径 | 要去除用户隐私 |
| 客服工单 | 高频问题、标准回复、处理流程 | 需要脱敏和去重 |
| 代码说明 | 模块职责、关键类、扩展点 | 不要直接塞完整仓库 |
| 运维手册 | 发布、回滚、监控、告警处理 | 要标注权限和环境 |
| 设计稿说明 | 页面状态、字段含义、交互边界 | 图片需要转文字说明 |

## 知识条目的最小字段

建议每个知识条目至少包含这些字段：

| 字段 | 作用 |
| --- | --- |
| `id` | 稳定唯一标识，增量同步时依赖它 |
| `title` | 人能看懂的标题，也方便检索结果展示 |
| `source_uri` | 来源地址，可以是文档链接、仓库路径、工单链接 |
| `body` | 进入检索的正文 |
| `tags` | 场景标签，例如 `android`、`crash`、`api` |
| `version` | 文档版本或业务版本 |
| `owner` | 维护团队或负责人 |
| `visibility` | 权限范围，例如 `public`、`internal`、`mobile-team` |
| `updated_at` | 最近更新时间 |

这些字段里，`id`、`source_uri`、`version` 和 `visibility` 最容易被忽略，但它们决定知识库能不能长期维护。

## 示例：Android 崩溃知识条目

```markdown
---
id: android-crash-guide
title: Android 崩溃排查知识
source_uri: app://knowledge/android/crash
tags: android, crash, logcat
version: v1
owner: mobile-team
visibility: internal
---

# Android 崩溃排查知识

NullPointerException、IllegalStateException、IndexOutOfBoundsException 是 Android 项目中常见的崩溃类型。
排查时先看 FATAL EXCEPTION 所在线程，再看 Caused by、业务堆栈、最近发布版本和用户操作路径。
```

这类条目比“崩溃怎么排查”这种泛泛描述更适合进入知识库，因为它有来源、标签、版本、维护人和具体排查路径。

## 数据源进入知识库前的判断

可以用四个问题快速判断：

1. 这份资料是否会被重复问到？
2. 它是否有明确来源和维护人？
3. 它是否能拆成独立、可引用的小片段？
4. 它是否包含敏感数据，需要脱敏或权限隔离？

如果四个问题都答不上来，先不要急着向量化。先补文档规范，后续检索效果会更稳定。

## 不推荐直接入库的内容

1. 大量过期聊天记录。
2. 没有结论的临时讨论。
3. 未脱敏的用户日志、手机号、身份证、Token。
4. 完整数据库导出。
5. 没有上下文的单行错误信息。
6. 自动生成但无人维护的重复文档。

知识库越大不一定越好。对 RAG 来说，稳定、可追溯、权限清晰的知识，比数量更重要。
