# 工具调用、状态与记忆

Agent 能多步骤执行，关键不在“模型更聪明”，而在应用给它提供了工具、状态和边界。

## 工具是什么

工具是应用暴露给模型的受控能力。常见工具包括：

| 工具 | 作用 |
| --- | --- |
| `search_knowledge_base` | 检索知识库 |
| `create_ticket` | 创建工单 |
| `query_log` | 查询日志 |
| `send_notification` | 发送通知 |
| `get_user_profile` | 读取当前用户信息 |
| `run_test` | 触发测试任务 |

工具不是模型自己执行的。模型只提出“我要调用哪个工具、参数是什么”，真正执行发生在你的应用侧。

## 工具 Schema

工具需要清晰的输入参数。一个工具 Schema 可以长这样：

```json
{
  "type": "function",
  "name": "search_knowledge_base",
  "description": "Search internal troubleshooting and product knowledge.",
  "strict": true,
  "parameters": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "Search query"
      }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

Schema 的价值是把模型输出约束成可执行参数，降低“生成一段自然语言但程序无法执行”的概率。

## 状态

Agent 每一步都需要状态。最小状态通常包含：

1. 用户目标。
2. 已调用工具列表。
3. 每次工具的输入和输出。
4. 当前任务状态。
5. 最大步数。
6. 是否需要人工审批。

这些状态不一定都要发给模型。有些只属于运行时，例如数据库连接、用户权限、内部配置。

## 记忆

Agent 里的“记忆”可以分成三类：

| 类型 | 示例 | 是否一定发给模型 |
| --- | --- | --- |
| 当前任务记忆 | 本次已经调用了哪些工具 | 部分需要 |
| 用户长期记忆 | 用户偏好、常用项目 | 看权限和必要性 |
| 系统运行时状态 | DB client、trace_id、API key | 不应该发给模型 |

记忆不是越多越好。模型只需要知道做决策所需的信息，其他状态留在应用侧。

## 停止条件

Agent 必须有停止条件：

1. 已经得到最终答案。
2. 达到最大步数。
3. 工具连续失败。
4. 需要人工审批。
5. 用户取消任务。
6. 权限不足。

没有停止条件的 Agent 容易陷入重复调用、成本失控或越权操作。

## Demo 中的简化模型

本阶段 Demo 使用 `ScriptedPlanner` 模拟模型决策：

1. 第一步调用 `search_knowledge_base`。
2. 如果目标里包含“工单”或“跟进”，再调用 `create_followup_ticket`。
3. 最后生成结果。
4. 如果 planner 一直不结束，`max_steps` 会强制停止。

这不是为了模拟模型能力，而是为了让你看清 agent loop 的工程结构。
