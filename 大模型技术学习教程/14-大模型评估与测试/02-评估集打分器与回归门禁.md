# 评估集、打分器与回归门禁

评估集是输入，打分器是判断标准，门禁是行动规则。三者缺一不可：只有用例没有打分器，就只能人工看；只有打分没有门禁，坏结果仍然可能上线。

## 打分器类型

| 类型 | 优点 | 缺点 | 适合场景 |
| --- | --- | --- | --- |
| 精确匹配 | 稳定、便宜 | 太死板 | 分类、固定字段 |
| 关键词覆盖 | 简单、可解释 | 容易漏判 | FAQ、政策问答 |
| JSON Schema | 工程稳定 | 只验证格式不验证事实 | 结构化输出 |
| 检索命中 | 能定位 RAG 问题 | 依赖文档标注 | 知识库问答 |
| LLM-as-judge | 灵活 | 成本高、有偏差 | 摘要、开放问答 |
| 人工评分 | 最可信 | 慢、贵 | 高风险业务 |
| Trace grading | 能看过程 | 需要记录完整轨迹 | Agent、多工具链路 |

第一版建议从规则打分开始。规则打分不高级，但它透明、便宜、容易放进 CI。

## 回归门禁

门禁不是只看一个总分。实际发布时可以组合多个指标：

```json
{
  "min_pass_rate": 0.9,
  "min_average_score": 0.85,
  "max_security_failures": 0,
  "max_cost_increase": 0.15,
  "max_latency_increase": 0.2
}
```

如果新版本总分提高，但安全用例失败，仍然不能上线。如果质量提升 1%，成本增加 80%，也需要业务确认。

## 失败样例要可行动

评估报告至少要告诉你：

1. 哪条用例失败。
2. 失败原因是什么。
3. 缺了哪些关键词或引用。
4. 当前版本和基线版本差异。
5. 失败更像是 Prompt、检索、模型、工具还是数据问题。

一个可行动的失败记录可以长这样：

```json
{
  "case_id": "refund-001",
  "score": 0.5,
  "missing_keywords": ["工作日"],
  "expected_source": "refund_policy_v3",
  "actual_source": "refund_policy_v1",
  "likely_owner": "retrieval"
}
```

## 版本化

评估集本身也要版本化。建议记录：

1. `eval_set_version`
2. `prompt_version`
3. `retriever_version`
4. `model`
5. `tool_schema_version`
6. `run_id`
7. `created_at`

否则你会遇到一个常见问题：这周的评估分和上周不一样，但没人知道是模型变了、Prompt 变了、文档变了，还是评估集变了。
