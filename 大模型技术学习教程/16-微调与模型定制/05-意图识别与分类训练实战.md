# 意图识别与分类训练实战

意图识别回答的是一个边界明确的问题：用户这句话希望系统完成哪类任务？本章用字符 n-gram、多项式朴素贝叶斯和一个版本化 JSON 制品，演示从数据校验到跨端部署的完整闭环。

核心文件：

- [训练与推理脚本](./demo/intent_classifier_demo.py)
- [三段式样例数据](./demo/sample_intents.jsonl)
- [Python/Java 一致性用例](./demo/intent_parity_cases.jsonl)
- [自动化测试](./demo/tests/test_intent_classifier_demo.py)

## 1. 问题边界

输入“帮我取消刚才的订单”时，意图分类只需要返回：

```json
{
  "intent": "cancel_order"
}
```

它不负责直接修改订单，也不负责补齐订单号。真实动作仍要经过后端鉴权、参数校验、幂等控制和必要的人工确认。

| 能力 | 回答的问题 | 示例 |
| --- | --- | --- |
| 意图分类 | 用户想做什么 | `cancel_order` |
| 槽位抽取 | 完成任务还缺什么参数 | `order_id=123` |
| RAG | 哪些资料能回答问题 | 检索退款规则 |
| Agent | 应按什么顺序调用工具 | 查订单后提交取消 |
| 生成式回答 | 应怎样向用户解释 | “订单已进入取消流程” |

本章只处理单标签、单层意图，不处理多标签、层级标签或槽位抽取。

## 2. 规则、Embedding、LLM 与分类器决策表

不要因为任务叫“意图识别”就默认训练模型。先选择最简单、能通过评估的方案。

| 方案 | 优先使用的场景 | 主要限制 | 需要保留的门禁 |
| --- | --- | --- | --- |
| 规则 | 标签少、表达固定、风险高且必须完全可解释 | 规则增长后容易冲突，长尾覆盖困难 | 冲突测试和兜底规则 |
| Embedding | 样例少、需要相似表达冷启动 | 文本相似不等于业务动作相同 | 相似度阈值和负例集 |
| LLM 结构化输出 | 标签变化快、已有模型链路、需要语义能力 | 有网络、成本和延迟，结果仍可能漂移 | Schema、固定评估集和超时降级 |
| 传统分类器 | 标签稳定、有中等规模标注数据、需要低成本离线推理 | 要维护数据、训练、校准和发布 | 三段式数据与拒识指标 |

推荐先做规则或 LLM Prompt 基线，再用同一评估集比较。只有当任务稳定且数据足够时，才值得引入分类器；更重的神经网络或微调应在当前方案达到能力瓶颈后再考虑。

## 3. 标签体系与 `unknown`

Demo 使用四个普通意图：

| 意图 | 定义 | 正例 | 容易混淆的边界 |
| --- | --- | --- | --- |
| `query_order` | 查询订单、物流或到货时间 | “包裹到哪里了” | 不包含取消动作 |
| `cancel_order` | 终止尚未完成的购买 | “撤销刚才的订单” | 不等于收货后退款 |
| `request_refund` | 要求退回已经支付的金额 | “申请退款” | 需要和取消订单分开 |
| `human_service` | 明确要求真人客服介入 | “转人工” | 抱怨不一定等于找人工 |

`unknown` 是系统发现证据不足或输入超出已知范围后的正确决策，不是一个包罗万象的业务类别。它只能出现在 `validation` 和 `test` 中，不能作为普通标签放进 `train`。

设计标签时应做到：

1. 名称使用稳定的小写蛇形业务动作。
2. 每个意图同时写清正例、反例和相邻意图边界。
3. 一条样本只保留一个主意图；需要多标签时升级任务设计。
4. 标签变化要版本化，并重新运行完整评估。
5. 线上无法安全执行的输入即使能分类，也不能绕过业务确认。

## 4. `train/validation/test` 三段式拆分

样例数据每行都是一个 JSON 对象：

```json
{"text":"我想取消刚才下的订单","intent":"cancel_order","split":"train"}
```

三个集合各自只有一个职责：

| split | 唯一用途 | 禁止事项 |
| --- | --- | --- |
| `train` | 拟合类别先验、词表和各类特征计数 | 不用于选择阈值 |
| `validation` | 搜索置信度与 margin 阈值 | 不写入模型统计量 |
| `test` | 阈值冻结后做一次最终报告 | 不参与训练、阈值或方案选择 |

纪律可以概括成三句话：只用 `train` 拟合，只用 `validation` 选阈值，`test` 在阈值冻结后仅报告一次。绝不能看完 test 结果再调阈值，然后仍把同一份结果称为独立测试。

真实项目可以按固定随机种子拆分，但用户、会话、时间相邻的模板化表达更适合按组拆分。否则同一表达的轻微改写会同时进入多个集合。

## 5. 泄漏检查

数据泄漏会让离线分数看起来很好，部署后却迅速退化。`validate` 会检查：

1. `text`、`intent`、`split` 是否完整且类型正确。
2. 意图名是否为小写蛇形命名，split 是否只含三个允许值。
3. 是否存在同集合重复、同文异标或跨集合完全重复。
4. 移除标点、空白并转小写后，是否出现跨集合近重复。
5. 每个训练意图是否同时有 validation 和 test 覆盖。
6. validation/test 是否出现训练集没有的普通意图，`unknown` 除外。
7. 三个集合是否为空，以及 `unknown` 是否误入 train。

例如“查询订单”和“查询，订单！”规范化后相同，不能一个放 train、另一个放 test。生产数据还应增加用户或会话分组、时间切分、模板来源和人工复核，避免只检查字符串后仍发生业务泄漏。

## 6. 字符 n-gram 与多项式朴素贝叶斯直觉

为了保持离线和零第三方依赖，Demo 使用下面的流程：

```text
文本
-> 整体转小写并只保留字母和数字
-> 提取字符 unigram 和 bigram
-> 统计每个意图下的特征频次
-> 拉普拉斯平滑后的对数概率
-> softmax 候选概率
```

例如：

```text
取消 -> 取 / 消 / 取消
```

字符 n-gram 不依赖中文分词，能捕捉“退款”“人工”“物流”等局部线索。多项式朴素贝叶斯先根据每类训练样本数估计类别先验，再根据特征在各类中的频次累计证据。拉普拉斯平滑让训练中未在某类出现的词不会直接把概率变成零。

预测只使用训练词表里的特征。规范化后为空，或所有特征都不在词表里时，模型不会强行猜测，而是返回 `unknown/no_features`。

这个模型的价值是小、可解释、能完整导出，不代表它理解了真正语义。复杂同义表达、多语言和分布漂移仍要通过真实评估决定是否换模型。

## 7. validation 阈值校准与确定性 tie-break

分类器总能选出第一名，但“最高”不等于“足够可靠”：

```text
confidence = 第一候选概率
margin = 第一候选概率 - 第二候选概率
```

Demo 只在 validation 上搜索：

```text
confidence: 0.35 / 0.45 / 0.55 / 0.65
margin:     0.05 / 0.10 / 0.20 / 0.30
最低已接受样本准确率: 0.75
```

先丢弃 `accepted_accuracy < 0.75` 的候选，再按以下固定顺序选择：

1. macro F1 更高。
2. coverage 更高。
3. confidence 阈值更低。
4. margin 阈值更低。

后两项是确定性 tie-break，保证同样的数据得到同样的选择。没有候选满足最低准确率时，训练直接失败，不静默发布低质量阈值。

推理结果的原因固定为：

| reason | 含义 |
| --- | --- |
| `no_features` | 没有任何训练词表可识别的特征 |
| `low_confidence` | 第一候选低于 confidence 阈值 |
| `low_margin` | confidence 足够，但前两名差距过小 |
| `accepted` | 同时通过两个阈值 |

判断顺序也是固定的：先检查 `no_features`，再检查 `low_confidence`，最后检查 `low_margin`。阈值写入制品后冻结，test 只能使用这组阈值做最终报告。

## 8. 分类指标与拒识指标

Accuracy 不能单独说明模型可用。若 90% 请求都是查订单，一个永远预测 `query_order` 的模型也可能得到很高 Accuracy。

| 指标 | 含义 |
| --- | --- |
| Precision | 被预测为某意图的样本中，有多少是真的 |
| Recall | 真实属于某意图的样本中，有多少被找出来 |
| F1 | Precision 和 Recall 的调和平均 |
| Macro F1 | 每个标签等权平均，避免大类掩盖小类 |
| 混淆矩阵 | 哪些真实标签经常被预测成另一个标签 |

混淆矩阵约定为“行 = 真实标签，列 = 预测标签”。拒识系统还必须同时报告：

| 指标 | 计算方式 |
| --- | --- |
| rejection rate | 被拒识数 / 全部样本数 |
| coverage | 被接受数 / 全部样本数 |
| accepted accuracy | 被接受且正确数 / 被接受数 |

不能只展示 accepted accuracy。把大部分困难样本都拒识，也能得到很高的已接受准确率，所以必须和 coverage、rejection rate、Macro F1 以及错误明细一起看。所有零分母在 Demo 中返回 `0.0`。

## 9. CLI 全流程

下面命令都在仓库根目录执行。模型写入 `$env:TEMP`，避免生成物进入 Git；先删除旧文件，是因为 `train` 默认拒绝覆盖已有制品。

```powershell
$demo = '.\大模型技术学习教程\16-微调与模型定制\demo\intent_classifier_demo.py'
$data = '.\大模型技术学习教程\16-微调与模型定制\demo\sample_intents.jsonl'
$model = Join-Path $env:TEMP 'intent-model.json'
Remove-Item -ErrorAction SilentlyContinue -LiteralPath $model

python $demo validate --data $data
python $demo train --data $data --model $model --model-version 'tutorial-v1'
python $demo evaluate --data $data --model $model --split test
python $demo predict --model $model --text '帮我取消订单'
python $demo inspect --model $model
```

五条命令的职责不同：

1. `validate` 校验 48 条样例及三段式数据契约。
2. `train` 只用 train 拟合、只用 validation 校准，再生成一个制品。
3. `evaluate` 加载已有制品及其中的冻结阈值，对指定 split 评估。
4. `predict` 加载已有制品并预测，示例应得到 `cancel_order/accepted`。
5. `inspect` 查看 schema、标签、阈值、数据 SHA-256 和紧凑统计，不打印全部特征计数。

`evaluate` 和 `predict` 都不会重新训练，也不会修改制品。artifact reload 是评估和部署边界：训练内存里的对象只能用于生成制品，后续结论必须基于重新加载的制品。

运行阶段 16 测试：

```powershell
$env:PYTHONDONTWRITEBYTECODE = '1'
python -m unittest discover -s '.\大模型技术学习教程\16-微调与模型定制\demo\tests' -p 'test_*.py'
```

## 10. 版本化 artifact schema

`train` 导出的 JSON 顶层结构固定为：

```json
{
  "schema_version": 1,
  "model_version": "tutorial-v1",
  "algorithm": "multinomial_naive_bayes",
  "normalization": {},
  "labels": [],
  "thresholds": {},
  "statistics": {},
  "training_metadata": {},
  "evaluation_summary": {}
}
```

| 字段 | 部署意义 |
| --- | --- |
| `schema_version` | 控制整体结构兼容性 |
| `model_version` | 关联发布、灰度和回滚 |
| `algorithm` | 防止加载器把统计量交给错误算法 |
| `normalization` | 固定 version 1、整体小写、字母数字过滤和 `[1, 2]` n-gram |
| `labels` / `statistics` | 保存有序标签、类别计数、特征计数、总数和词表 |
| `thresholds` | 保存 validation 选择的 confidence、margin 和最低准确率 |
| `training_metadata` | 保存 UTC 训练时间、split 数量和数据 SHA-256 |
| `evaluation_summary` | 保存 validation 与 test 的紧凑报告 |

跨端规范化基线固定为 Python 3.13 的 Unicode 15.1 行为；Java 端把相关小写和字母数字表固化在代码中，避免不同 JDK 的 Unicode 版本改变结果。`normalization.version=1` 就代表这份契约，改变算法或规范化行为必须升级版本。

导出使用 UTF-8、稳定键排序和同目录临时文件，写完并刷新后再发布。加载器会拒绝未知 schema、额外或缺失字段、非法阈值、负计数、标签或词表不一致等损坏制品。

同一个 artifact 配合同一份 [parity cases](./demo/intent_parity_cases.jsonl)，可以验证 Python 与 Java 的标签、拒识原因、候选顺序和浮点概率没有漂移。只比较最终标签会漏掉排序或阈值边界问题。

## 11. 生产迁移边界

这个 Demo 展示的是部署契约，不是完整训练平台或 Android 工程。

| Demo | 生产实现还要补齐 |
| --- | --- |
| 小型 JSONL | 版本化数据集、标注审核、隐私扫描和访问控制 |
| 字符 n-gram | 与规则、Embedding、神经分类器或微调模型做同集对比 |
| 固定阈值网格 | 根据误操作成本、人工承接容量和用户群分层校准 |
| 本地 JSON 制品 | 模型注册、签名清单、灰度、回滚和发布审批 |
| 离线报告 | 线上漂移、覆盖率、拒识原因和人工纠错监控 |
| 单一中文客服场景 | 多语言、渠道、攻击输入和设备差异评估 |

线上回流不能把用户原文直接写入普通日志。应先脱敏、获得合规依据、人工复核标签，再进入下一版数据。任何从失败样本得到的修改都先作用于 train/validation；旧 test 一旦参与分析，就应视为开发数据并准备新的独立 test。

### 小练习

1. 为自己的业务定义四个意图，每类写正例、反例和相邻边界。
2. 每类准备 train、validation、test，并为后两者增加域外 `unknown`。
3. 运行五条 CLI 命令，记录 model version、数据 SHA-256 和阈值。
4. 找出混淆最多的一对意图，同时比较 Macro F1、coverage 和 accepted accuracy。
5. 只修改 train/validation 后训练新版本，保留 test 到阈值冻结后再报告。

### 本章小结

可部署的意图分类不只是“训练出一个标签”。真正需要保留的是稳定的标签边界、三段式数据纪律、可解释拒识、分类与覆盖指标、版本化制品，以及基于同一制品的跨运行时验证。
