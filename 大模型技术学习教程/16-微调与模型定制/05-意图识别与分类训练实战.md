# 05. 意图识别与分类训练实战

意图识别回答的是一个边界明确的问题：用户这句话希望系统完成哪类任务？

例如电商客服里的输入：

```text
帮我取消刚才的订单
```

可以分类为：

```json
{
  "intent": "cancel_order"
}
```

这类任务看起来简单，但真正上线时需要处理标签边界、相似意图、数据泄漏、类别不平衡、置信度、拒识和线上错误回流。本章用一个纯 Python 标准库 Demo 把这些步骤串成闭环。

## 1. 先分清意图识别不是什么

| 能力 | 回答的问题 | 示例 |
| --- | --- | --- |
| 意图识别 | 用户想做什么 | `cancel_order` |
| 槽位抽取 | 完成任务还需要哪些参数 | `order_id=123` |
| RAG | 哪些资料能回答问题 | 检索退款规则 |
| Agent | 需要按什么步骤调用工具 | 查订单后提交取消 |
| 生成式回答 | 应该怎样向用户解释 | “订单已进入取消流程” |

意图识别只负责做判断，不应该直接修改订单。真实动作仍然需要后端鉴权、参数校验、幂等控制和必要的人工确认。

## 2. 是否一定需要训练

先根据任务规模和风险选择最简单的可行方案：

| 方案 | 适合场景 | 主要限制 |
| --- | --- | --- |
| 关键词和规则 | 意图少、表达固定、需要完全可解释 | 规则多后容易冲突，覆盖长尾表达困难 |
| Embedding 相似度 | 样例少、需要快速冷启动 | 相似文本不一定具有相同业务意图 |
| 大模型结构化输出 | 意图变化快、样例少、已经有模型调用链路 | 有调用成本和延迟，仍需 Schema 与评估 |
| 传统分类器 | 有稳定标签和中等规模标注数据 | 需要维护训练、评估和发布流程 |
| 小模型微调 | 量大、任务稳定、现有方案达到瓶颈 | 数据和平台成本更高，回滚更复杂 |

推荐顺序是：

```text
规则或 Prompt 基线 -> 建立评估集 -> 分析错误
-> 数据足够且任务稳定后再训练或微调
```

不要因为任务叫“意图识别”就默认必须训练模型。

## 3. 设计意图体系

本章 Demo 使用四个业务意图：

| 意图 | 定义 | 正例 | 容易混淆 |
| --- | --- | --- | --- |
| `query_order` | 查询订单、物流或到货时间 | “包裹到哪里了” | 不包含取消动作 |
| `cancel_order` | 终止尚未完成的购买 | “撤销刚才的订单” | 不等于收货后退款 |
| `request_refund` | 要求退回已经支付的金额 | “申请退款” | 可能需要售后条件 |
| `human_service` | 明确要求真人客服介入 | “转人工” | 抱怨不一定等于找人工 |

还需要一个特殊结果：

```text
unknown
```

`unknown` 不是“模型失败”，而是系统发现当前证据不足或输入不属于已知业务范围后的正确决策。例如“今天天气怎么样”就不应该被强行归入订单意图。

### 标签设计原则

1. 名称使用稳定的业务动作，不使用页面名称或临时活动名称。
2. 每个意图同时写清正例、反例和相邻意图边界。
3. 同一句话只能有一个主意图；确实需要多标签时，应升级任务设计。
4. 不要把“其他”样本全部塞进一个巨大的训练类别。
5. 标签变化要版本化，并重新运行完整评估集。

## 4. 标注和拆分数据

Demo 的每行 JSONL 都包含：

```json
{"text":"我想取消刚才下的订单","intent":"cancel_order","split":"train"}
```

字段含义：

| 字段 | 含义 |
| --- | --- |
| `text` | 用户原始表达 |
| `intent` | 人工确认的标准标签 |
| `split` | `train` 或 `test` |

### 为什么固定 split

教学 Demo 把拆分结果直接写进数据文件，原因是每次运行都应该得到相同结果。真实项目可以按固定随机种子拆分，但还要防止这些泄漏：

- 同一文本同时出现在训练集和测试集。
- 只改标点或空格的近重复文本跨集合出现。
- 同一用户的模板化表达被随机拆到两边。
- 测试集被反复拿来调整规则、阈值或 Prompt。

如果你根据测试集失败样例改完模型，又继续用同一批数据宣称效果提升，这批数据实际上已经变成开发集。此时应保留另一份独立评估集做最终判断。

### 数据质量检查

本章 Demo 会检查：

1. `text`、`intent`、`split` 是否完整。
2. 意图名是否为小写蛇形命名。
3. split 是否只有 `train` 和 `test`。
4. 是否存在重复文本或冲突标签。
5. 每个训练意图是否有测试样本。
6. 每个测试意图是否能在训练集中找到，`unknown` 除外。

生产数据还应该记录来源、标注人、审核人、业务版本、语言和敏感信息状态。

## 5. Demo 使用什么分类器

为了保持离线和零依赖，Demo 实现了一个多项式朴素贝叶斯分类器：

```text
文本
-> 小写并移除空白和标点
-> 提取字符 unigram 和 bigram
-> 统计各意图下的特征频次
-> 计算每个意图的对数概率
-> softmax 转成候选概率
```

例如：

```text
取消 -> 取 / 消 / 取消
```

字符 n-gram 不需要中文分词库，适合演示文本如何变成特征。它不是生产推荐模型，也不能理解真正的语义；它的价值是让训练、预测和评估过程完全可观察。

## 6. 不能只看 Accuracy

假设 90% 的请求都是“查订单”，一个永远预测 `query_order` 的分类器也有 90% Accuracy，但其他意图全部不可用。

分类任务至少要看：

| 指标 | 含义 |
| --- | --- |
| Precision | 被预测为某意图的样本中，有多少是真的 |
| Recall | 真实属于某意图的样本中，有多少被找出来 |
| F1 | Precision 和 Recall 的调和平均 |
| Macro F1 | 每个意图 F1 等权平均，避免大类别掩盖小类别 |
| 混淆矩阵 | 哪些真实意图经常被预测成另一个意图 |

本 Demo 的混淆矩阵约定是：

```text
行 = 真实标签 actual
列 = 预测标签 predicted
```

例如 `confusion_matrix.query_order.cancel_order = 1` 表示有一个真实的查单问题被错误预测成取消订单。

## 7. 用置信度和 margin 做拒识

分类器总能选出概率最高的标签，但“最高”不代表“足够可靠”。Demo 同时检查：

```text
confidence = 第一候选概率
margin = 第一候选概率 - 第二候选概率
```

满足任一条件时返回 `unknown`：

1. 文本没有可用特征。
2. `confidence` 低于阈值。
3. `margin` 低于阈值，说明前两名难以区分。

拒识结果仍然保留候选项：

```json
{
  "intent": "unknown",
  "confidence": 0.39,
  "margin": 0.08,
  "reason": "low_confidence",
  "candidates": [
    {"intent": "query_order", "probability": 0.39},
    {"intent": "human_service", "probability": 0.31}
  ]
}
```

这样可以区分“没有任何线索”和“两个业务意图非常接近”，也方便后续回流标注。

阈值必须通过评估集选择。提高阈值通常会减少误判，但增加 `unknown`；降低阈值则相反。

```json

  "valid": true,
```

```powershell

```

输出包含：

- 测试样本数和 Accuracy；
- 混淆矩阵；

## 9. 如何分析当前 Demo 的错误

不要只追求把示例分数调成 100%。先看错误明细：

1. 是标签边界不清，还是样本表达覆盖不足？
2. 是 `query_order` 和 `cancel_order` 共享“订单”造成混淆吗？
3. 是否应该增加能区分动作的表达，例如“物流”“撤销”“退回金额”？
4. 某个意图是否样本过少，或只覆盖一种说法？
5. 阈值变化改善了误判，还是只把问题变成更多 `unknown`？

修正流程应该是：

```text
查看错误 -> 判断失败类型 -> 补充或修正标注
-> 保持独立评估集 -> 重新训练 -> 比较每类指标
```

不要直接把测试样本复制进训练集。应该补充同类但不同表达的训练样本，并保留原测试样本验证泛化。

## 10. 迁移到真实项目

本 Demo 迁移到生产环境时，至少要补齐：

| Demo | 生产实现 |
| --- | --- |
| 小型 JSONL | 版本化数据集和审核记录 |
| 字符 n-gram | 经过评估的 Embedding、分类模型或微调模型 |
| 每次 CLI 重新训练 | 模型制品、版本、发布和回滚 |
| 固定阈值 | 按业务风险和评估结果校准 |
| 离线错误列表 | 线上反馈、抽检和标注回流 |
| 单一中文场景 | 多语言、渠道、用户群和分布漂移监控 |

即使换成更强的模型，下面这些资产仍然需要保留：

- 意图定义和边界；
- 标注规范；
- 独立评估集；
- 混淆矩阵和分类指标；
- `unknown` 与人工兜底；
- 数据、模型和阈值版本。

## 11. 小练习

为你自己的业务设计四个意图：

1. 为每个意图写定义、三个正例和两个反例。
2. 每类准备至少六条训练样本和三条测试样本。
3. 增加三个域外问题，期望标签为 `unknown`。
4. 运行 `validate` 和 `evaluate`。
5. 找出混淆最多的一对意图。
6. 只修改训练数据或阈值，再次评估并解释变化。
7. 说明这个任务最终应该使用规则、大模型结构化输出、传统分类器还是微调。

完成后，你应该能够解释：意图分类的难点通常不在“调用哪个模型”，而在标签边界、训练数据、独立评估和安全拒识。
