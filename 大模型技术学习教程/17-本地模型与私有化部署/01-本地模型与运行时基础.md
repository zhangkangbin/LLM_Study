# 本地模型与运行时基础

本地模型是指模型权重和推理运行时由你自己管理，运行在本机、公司服务器、私有云或边缘设备上。它常见于隐私要求高、网络隔离、成本可控、离线可用或需要定制运行环境的场景。

## 常见运行方式

| 方式 | 适合场景 |
| --- | --- |
| 桌面本地运行 | 学习、原型、离线助手 |
| 单机服务 | 内部工具、小并发 |
| GPU 推理服务 | 企业知识库、高并发 |
| Kubernetes 部署 | 多租户、弹性伸缩 |
| 边缘设备 | 低延迟、离线、现场设备 |

## 运行时关注点

1. 模型格式和量化。
2. 显存/内存占用。
3. 上下文长度。
4. 并发和吞吐。
5. 流式输出。
6. 监控和日志。
7. 授权和许可证。

不要只看“能不能跑起来”。生产环境要看它能否稳定服务真实流量。

## 常见运行时形态

| 形态 | 你要关心什么 |
| --- | --- |
| 本地桌面工具 | 易用性、模型下载、离线体验、隐私提示 |
| 单机 HTTP 服务 | 并发、超时、流式输出、日志、服务重启 |
| 专用推理服务 | 批处理、队列、KV cache、GPU 利用率、模型热切换 |
| Kubernetes 推理集群 | 调度、弹性、镜像、节点池、灰度、资源隔离 |
| 端侧小模型 | 包体、发热、电量、设备差异、离线兜底 |

学习阶段可以先跑桌面或单机服务；生产阶段通常还需要队列、限流、监控和回退。

## 粗略显存估算

一个非常粗略的估算：

```text
参数量(十亿) * 量化位数 / 8 = 权重占用 GB
```

例如 7B 模型使用 4-bit 量化，权重大约是：

```text
7 * 4 / 8 = 3.5 GB
```

实际还要加上 KV cache、运行时开销、并发、上下文长度和系统余量。

更完整的估算至少要考虑：

| 项 | 影响 |
| --- | --- |
| 权重内存 | 和参数量、量化位数有关 |
| KV cache | 和上下文长度、并发数、模型结构有关 |
| 运行时开销 | 框架、CUDA、batch、tokenizer、服务进程都会占内存 |
| 并发队列 | 排队会增加延迟，过度并发会让吞吐下降 |
| 上下文长度 | 长上下文不只增加输入 token，也会放大 KV cache |
| 余量 | 生产环境不要把显存打满，预留故障和波动空间 |

粗略评估流程：

1. 先估算模型权重能不能放下。
2. 再估算目标上下文和并发下的 KV cache。
3. 再压测首 token 延迟、吞吐和总耗时。
4. 最后决定是否需要更小模型、量化、缩短上下文、增加机器或改路由。

## 选模型时不要只看参数量

私有化选型还要看：

1. 许可证是否允许商用和内部分发。
2. 是否支持目标语言和领域。
3. 是否支持需要的上下文长度。
4. 是否支持流式输出和工具调用格式。
5. tokenizer 是否适合中文、代码和日志。
6. 推理框架是否稳定，社区和文档是否活跃。
7. 是否能接入现有监控和日志。

一个较小但稳定、可观测、可回退的模型，往往比一个“看起来更强但难运维”的模型更适合第一版。

## 压测指标

本地模型上线前至少压这些指标：

| 指标 | 为什么重要 |
| --- | --- |
| 首 token 延迟 | 用户何时看到反馈 |
| tokens/s | 生成速度 |
| 并发请求数 | 服务能承受多少同时请求 |
| P95/P99 总耗时 | 尾延迟是否可接受 |
| GPU 利用率 | 资源是否浪费或打满 |
| 显存占用 | 是否接近 OOM |
| 队列长度 | 是否需要限流或扩容 |
| 错误率 | 是否有超时、断流、OOM |

压测要用接近真实的 Prompt 和上下文长度。只用一句“你好”压出来的数据没有参考价值。

## 本地模型不等于安全

本地部署可以减少数据出边界，但不自动解决：

1. Prompt 注入。
2. 越权工具调用。
3. 日志泄露。
4. 模型输出不可信。
5. 训练数据或模型许可证问题。
6. 内部用户滥用。

安全边界仍然要做在网关、权限和审计层。

## 本章小结

本地模型的核心问题不是“能不能跑”，而是“能不能稳定、可控、可观测地服务真实业务”。私有化之前，先把数据敏感度、流量、模型能力、许可证、硬件、运维和降级策略都写清楚。
