# 团队规范、知识沉淀与效率度量

AI 编程要在团队里稳定发挥作用，需要把经验沉淀成规范，而不是存在某个人的聊天记录里。

## 可以沉淀什么

1. 项目结构说明。
2. 常用构建和测试命令。
3. 代码风格。
4. Review 重点。
5. 安全边界。
6. 发布流程。
7. 常见问题排查步骤。

这些可以写进项目文档、AGENTS.md、脚本、模板或内部知识库。

## AGENTS.md 示例

可以在仓库根目录放一个简短版本：

```markdown
# AGENTS.md

## 项目约定
- Android 端不保存模型供应商 API Key。
- AI Gateway 负责模型调用、Prompt、RAG 权限和工具执行。
- ViewModel 状态变更必须有单元测试。

## 常用命令
- 单元测试：`./gradlew :app:testDebugUnitTest`
- 后端测试：`pytest tests`
- Markdown 链接检查：`python scripts/check_links.py`

## 修改规则
- 先读相关文件和测试，再改代码。
- 保持最小改动，不做无关重构。
- 修改 Prompt、Schema、RAG 策略时，必须更新评估用例。
- 涉及用户隐私、权限、工具执行的变更必须人工 Review。

## 输出要求
- 说明改了什么。
- 说明运行了哪些验证命令。
- 说明剩余风险。
```

AGENTS.md 不要写成大而全的公司制度。它应该回答“这个仓库里，AI 和人一起改代码时必须知道什么”。

## 团队提示模板

```text
请先阅读相关代码并说明影响范围。
实现时保持最小改动。
新增或修改测试。
完成后运行：
- ./gradlew :app:testDebugUnitTest
- ./gradlew :app:assembleDebug
最终说明修改内容、验证结果和剩余风险。
```

模板的作用是降低沟通成本，也减少 AI 忘记验证的概率。

## 常用模板库

建议把高频工作沉淀成模板：

| 模板 | 适合任务 |
| --- | --- |
| Bug 定位模板 | 崩溃、状态错乱、接口失败 |
| Review 模板 | PR 风险检查、发布前检查 |
| 测试生成模板 | ViewModel、Repository、JSON 解析、权限 |
| 文档更新模板 | README、接口文档、上线手册 |
| 评估集补充模板 | Prompt、RAG、Agent 回归 |

示例：评估集补充模板。

```text
这次变更影响了大模型回答质量。
请根据 diff 补 3 条评估用例：
1. 正常命中
2. 无答案拒答
3. 边界/安全问题

每条用例包含：
- id
- input
- expected_source
- required_keywords
- forbidden_keywords
```

## 效率指标

不要只看“AI 写了多少行代码”。更有价值的指标：

1. Bug 修复平均耗时。
2. 测试覆盖的关键路径。
3. Review 发现问题数量。
4. 回归缺陷减少情况。
5. 文档更新及时性。
6. 新人理解代码耗时。

## 质量指标

效率提升不能以质量下降为代价。建议同时看：

1. AI 参与 PR 的回滚率。
2. AI 参与 Bug 修复后的复发率。
3. AI 生成测试的真实失败捕获率。
4. Review 发现的 P0/P1 问题数量。
5. 文档和代码是否同步更新。
6. 评估集是否随 Prompt/RAG 变化更新。

如果“交付更快”伴随“回归更多”，说明流程缺少验证门禁。

## 风险控制

团队使用 AI 时要明确：

1. 哪些代码不能上传外部工具。
2. 哪些日志必须脱敏。
3. 哪些变更必须人工 review。
4. 哪些命令不能自动执行。
5. 如何处理 AI 生成代码的许可证和来源风险。

AI 是研发加速器，不是责任转移器。

## 团队落地路径

建议分三步：

1. 个人试点：先在低风险任务中使用 AI，记录有效提示和失败案例。
2. 小组模板：沉淀 AGENTS、Review 模板、测试模板和常用命令。
3. 流水线门禁：把测试、评估、链接检查、安全扫描接入 CI 或发布流程。

不要一开始就强推复杂规范。先找一个真实高频场景，比如“Android 崩溃定位 + 测试补齐”，跑通后再推广。

## 本章小结

团队 AI 编程的长期价值来自沉淀，而不是一次聊天。把任务模板、验证命令、Review 清单、评估用例和失败复盘写进仓库，AI 才能越来越懂这个项目。
