# 里程碑拆解与实现顺序

综合项目要按可交付里程碑推进。每个里程碑都能运行、能演示、能测试。

不要按“先做完整后端、再做完整 Android、最后补测试”的方式推进。大模型项目更适合纵向切片：每个里程碑都从客户端输入走到后端、模型/RAG、日志和验收。

## M1：MVP

目标：

1. Android 文本聊天界面。
2. 后端 `/api/chat`。
3. 固定 Prompt。
4. 流式输出。
5. 基础日志。

验收：

1. 能问一个问题并看到流式回答。
2. 断网和取消有状态。
3. 后端记录 requestId、模型、token、延迟。

任务顺序：

1. 定义 `/api/chat` 请求体和流式事件协议。
2. Android 端创建最小聊天页面：输入框、发送按钮、消息列表、加载状态。
3. Android 端实现 `ChatUiState`：`Idle`、`Sending`、`Streaming`、`Completed`、`Failed`、`Cancelled`。
4. 后端实现 `AI Gateway` 的假模型客户端，先返回固定流式事件。
5. 后端加入 requestId、userId、promptVersion、modelRoute 日志。
6. Android 接入真实后端流式事件，并支持取消。
7. 为 ViewModel 状态机、后端请求日志和流式事件转换补测试。

M1 不要求回答质量很高，但必须证明端到端链路稳定。

## M2：知识库增强

目标：

1. 文档导入。
2. 清洗、切分、Embedding。
3. 向量检索。
4. 回答带引用。
5. 第一版评估集。

验收：

1. 10 条知识库问题命中正确文档。
2. 回答显示引用。
3. 知识库无答案时能拒答。

任务顺序：

1. 准备第一批知识库文档：崩溃排查、ANR 排查、接口错误、发布回滚、代码规范。
2. 为文档补元数据：`docId`、`title`、`sourceUri`、`version`、`visibility`、`owner`、`tags`。
3. 实现文档清洗和切分，生成 `chunks.jsonl`。
4. 实现第一版检索：可以先用本地 toy embedding 或关键词检索，后续替换为真实向量库。
5. 在检索前加入权限过滤。
6. 修改 Prompt：要求模型只基于检索片段回答，并在资料不足时拒答。
7. Android 端展示引用卡片，并支持点击跳转内部文档。
8. 建立第一版 10 到 20 条 RAG 评估集。

M2 的核心不是“模型回答得更会说”，而是“回答有依据、引用可追踪、无资料能拒答”。

## M3：多模态体验

目标：

1. 语音输入。
2. 图片/截图提问。
3. TTS 播报。
4. Android 状态机完善。

验收：

1. 权限拒绝有提示。
2. 录音取消不残留任务。
3. 图片上传失败可重试。

任务顺序：

1. 增加语音输入入口，先做“录音 -> 上传 -> 转写 -> 文本问答”的普通链路。
2. 增加 TTS 播报，但保留文本结果作为主输出。
3. 增加图片/截图提问入口，上传前给出明确用户触发。
4. 后端扩展请求体，支持 `attachments`。
5. 后端对音频、图片做大小、类型、权限和脱敏检查。
6. Android 增加权限状态：未授权、录音中、上传中、转写中、生成中、失败可重试。
7. 为取消、后台切换、上传失败、权限拒绝补状态机测试。

M3 不急着上 Realtime。普通语音链路稳定后，再决定是否需要低延迟实时对话。

## M4：上线准备

目标：

1. 完整评估集。
2. 安全红队用例。
3. 监控告警。
4. 灰度和回滚。
5. 发布文档。

验收：

1. 质量评估通过。
2. 高危安全用例通过。
3. 成本和延迟有阈值。
4. 可以切换模型或 Prompt 版本。

任务顺序：

1. 扩展评估集：高频问题、无答案问题、权限问题、多轮问题、安全问题。
2. 建立发布门禁：通过率、平均分、安全失败数、成本增长、延迟增长。
3. 接入监控：请求数、错误率、首 token 延迟、总耗时、token、成本、拒答率。
4. 增加灰度配置：模型版本、Prompt 版本、检索策略版本。
5. 增加回滚路径：模型回滚、Prompt 回滚、知识库版本回滚。
6. 增加红队用例：Prompt 注入、泄露系统提示词、越权工具、伪造引用、不可信 HTML。
7. 写上线手册：发布步骤、回滚步骤、告警处理、事故复盘模板。

M4 的目标是让系统可以被团队长期维护，而不是只在演示时看起来能跑。

## 推荐时间线

| 周期 | 交付物 | 验证方式 |
| --- | --- | --- |
| 第 1 周 | M1 文本问答闭环 | Android 可发送问题，后端有日志，状态机测试通过 |
| 第 2 周 | M2 知识库问答 | 10 到 20 条评估集可运行，引用可展示 |
| 第 3 周 | M3 语音/图片入口 | 权限、取消、上传失败和重试场景可演示 |
| 第 4 周 | M4 上线准备 | 评估门禁、安全用例、监控指标和回滚手册齐全 |

时间线可以拉长，但顺序不要反过来。先做闭环，再做质量；先有日志，再谈优化。

## 每个里程碑都要保留的证据

每完成一个里程碑，至少保存这些证据：

1. 关键接口请求和响应样例。
2. Android 状态截图或录屏。
3. 后端日志样例。
4. 测试命令和结果。
5. 评估集运行结果。
6. 已知问题和下一步计划。

没有证据的“完成”很难复盘，也很难交接给团队。

## 顺序原则

先做闭环，再做智能；先做可观测，再做复杂；先做可回滚，再做自动化。
