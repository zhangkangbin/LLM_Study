# 阶段练习与自检

这个文件把 21 个阶段统一映射到同一个贯穿项目：

```text
Android 知识库助手 / Android 崩溃日志智能分析工具
```

每学完一个阶段，都建议完成一个小练习，再用自检问题判断是否可以进入下一阶段。

## 意图分类跨端自检

阶段 16 和 17 的联合练习不是复用一个手工挑选的旧模型，而是从样例数据训练一个新 artifact，再让 Python 和 Java 加载同一个文件、读取同一份 `intent_parity_cases.jsonl`。

仓库测试已经自动化这条路径：

```powershell
$env:PYTHONDONTWRITEBYTECODE = '1'
python '.\大模型技术学习教程\16-微调与模型定制\demo\tests\test_intent_classifier_demo.py' JavaIntentClassifierParityTest
```

可执行判定标准：

1. 命令退出码为 `0`，结果为 `OK`，且 Java 测试没有因缺少 `javac` 或 `java` 被 skip。
2. Python CLI 在临时目录训练新 artifact；Python 与 Java 后续都重新加载这同一个文件，不在比较时重新训练。
3. 两端对同一 parity case 的 `intent`、`reason` 和 candidate intent 顺序完全相同。
4. 每个 candidate probability、confidence 和 margin 的绝对误差不超过 `1e-9`。
5. 用例同时覆盖四个已知意图、`no_features`、`low_confidence`、`low_margin`、拉丁字母、数字和中英混合输入。

## 生成模型训练与本地部署自检

阶段 16 和 17 的生成模型联合练习以[训练与量化章节](./16-微调与模型定制/06-面向端侧的生成模型训练与量化.md)和[本地部署章节](./17-本地模型与私有化部署/05-Ollama与llama.cpp本地部署实战.md)为准。仓库验收不要求下载模型、使用 GPU 或生成 GGUF；真实训练和推理要在有相应环境时完成，并保留以下可检查产物。

1. **验证 Chat JSONL**。输入是 `sample_mobile_llm_chat.jsonl`；运行下面命令，输出分别保存为 `dataset-validation.json` 和 `dataset-summary.json`。通过标准是两个命令退出码都为 `0`，校验结果的 `valid` 为 `true`、`issues` 为空，摘要的 `split_counts` 包含 train/validation/test。

   ```powershell
   python '.\大模型技术学习教程\16-微调与模型定制\demo\mobile_llm_dataset_demo.py' validate > dataset-validation.json
   python '.\大模型技术学习教程\16-微调与模型定制\demo\mobile_llm_dataset_demo.py' summarize > dataset-summary.json
   ```

2. **记录 base baseline**。输入是冻结的 base model commit、独立 Prompt Suite 及其 SHA-256、固定生成参数和 chat template 设置；输出是只创建一次、不覆盖的 `base-baseline.jsonl`。通过标准是每个 Prompt 都记录原始输出、任务结果、拒绝/格式判定、延迟和运行配置，且文件内的 model commit 与 suite hash 和实验记录一致。
3. **说明一个 LoRA 和一个 QLoRA 选择**。输入是同一 base、数据规模、可用显存、目标层检查结果和质量门槛；输出是 `adapter-decisions.md`，分别写出 LoRA 与 QLoRA 的精度、显存、速度和后端约束，并明确本次实验选哪一个。通过标准是 LoRA 方案不错误启用 4 bit，QLoRA 方案明确 NF4、计算 dtype 和硬件前置条件，两者都记录实际 target modules，不盲抄层名。
4. **写 GGUF manifest 草稿**。输入是 base/adapter/merged 路径或制品 ID、模型与数据 commit/hash、tokenizer/chat template、llama.cpp commit、转换与量化命令；输出是 `gguf-manifest-draft.json`。通过标准是即使权重尚未生成，仍预留 merged、F16 GGUF、Q4_K_M GGUF 的 SHA-256、字节数和评测报告字段，并且不包含 token、密码或用户隐私。
5. **运行一个 Ollama HTTP 请求**。输入是已在本机可用的模型名和 Prompt；运行下面的非流式请求，输出保存为 `ollama-evidence.json`。通过标准是 HTTP 成功、`result.response` 非空，而且证据同时记录 Ollama 版本、完整请求和服务端耗时；如果本机尚无模型，先保留请求体和预期响应契约，待部署环境就绪后再完成运行证据。

   ```powershell
   $Version = (ollama --version | Out-String).Trim()
   if ($LASTEXITCODE -ne 0) { throw 'Ollama CLI 不可用' }
   $Request = [ordered]@{ model = 'qwen3:0.6b'; prompt = '请用一句话说明如何查询订单'; think = $false; stream = $false; options = @{ num_ctx = 2048 } }
   $Body = $Request | ConvertTo-Json -Depth 4
   $Result = Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:11434/api/generate' -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($Body)) -TimeoutSec 120
   [ordered]@{ recorded_at = (Get-Date).ToUniversalTime().ToString('o'); ollama_version = $Version; request = $Request; result = $Result } | ConvertTo-Json -Depth 8 | Set-Content -Encoding UTF8 ollama-evidence.json
   ```

6. **比较 Ollama 与 llama.cpp**。输入是同一个 GGUF、同一组 Prompt、chat template/thinking 模式、context、temperature、seed 和输出上限；输出是 `runtime-comparison.md`。通过标准是逐项记录输出质量、拒绝和格式结果、首 token/总延迟、生成速度、峰值内存、冷/热启动及完整命令，并解释差异；模型或参数不一致时不得下跨运行时结论。

## 使用方式

1. 学完一个阶段，先做对应小练习。
2. 再回答自检问题，不要只看答案是否“像那么回事”。
3. 如果答不清，回到该阶段 README 和章节正文。
4. 如果能答清，把练习产物沉淀到综合项目文档里。
